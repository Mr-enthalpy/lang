**Status: Future design narrative for value/extraction behavior. Not current
implementation behavior.** The old formal meta-return split in this document is
superseded by
`spec/design/symbol-world/symbol-first-meta-construction-and-pattern-injection.md`,
which is the canonical first read for symbol construction, `compile` / `meta`,

## 1. Values First

An evaluation returns one result object, whose normal form may be an ordinary
value `e` or a product value `P`:

```text
e:
  ordinary non-product value point

P:
  product value / product normal form
```

A meta constructor call returns an ordinary value. A multi-member result is an
ordinary Symbol PatternValue; the current implementation carries it temporarily
as `SymbolConstructionValue`:

```text
(int Vec::std)
```

This is not a `TypeValueId`. It is the value formed by the construction
expression `(int) |> Vec::std`. Type computation is only one projection of that
value, not its definition.

**Notation.** This document uses `(int Vec::std)` as the complete canonical
meta-instance navigation atom and `(int) |> Vec::std` as the pipe/call skeleton
from which it is derived. The callee path remains inside the invocation
parentheses. Neither `(int Vec)::std` nor unparenthesized `int Vec::std` denotes
that instance.

**Governing rank principle.** The value world composes under one principle
(canonical detail: `symbol-world/type-values-places-and-borrow-views.md` §2.3):

1. Ordinary structural content is governed by `Object = <Val1?, P, Val2>`.
2. Complete types are rank-indexed closures `tau = <Q, V_τ>` over that Object
   material; `tau` participates in Pattern observation through `Core(tau) = Q`
   and is not itself an ordinary Object.
3. Ordinary computation preserves the declared semantic rank
   (`OrdinaryRankPreservation`); place projection, borrow lifting, and type
   formation compose by the ordinary typing/naturality laws, e.g.
   `TypeOf(Ref(p)) = RefTy(TypeOf(Read(p)))`.

## 2. The Hourglass

A construction value of a Pattern family that declares the corresponding
interfaces is a waist point:

```text
        extraction pattern space
              ↑
              |
        construct / extract
              |
              ↓
          value point e
              |
              ?
              ↓
        exposed extraction view e' or P
```

Upward: that specific family may prove a constructor/extractor isomorphism
(`construct_C(P) = v`, `extract_C(v) = P`). This is not an axiom of the base
Pattern relation.

Downward: `?` attempts to peel one top Pattern layer.

## 3. `?` Peels One Top Pattern Layer

`?` does not mean "destructure" and is not required to begin extraction.
Destructuring happens only when a pattern matcher reads the symbol's Pattern
layer and consumes product normal form.

```text
leaf? = leaf
P? = P
TopPattern(P)? = P
x?? = (x?)?
```

A future design may allow a constructor to declare a bounded custom exposed
view, but the current default remains exactly one top-Pattern peel. Bare `?` is
not the constructor-specific inverse extractor. The upward `construct_C` /
`extract_C` isomorphism and the downward `?` view transition are separate
paths. Extracting a type parameter (for example from `Vec::std`) requires the
constructor-specific extractor in a rank-pattern context, not bare `?`.

The future extraction view produced by a successful peel must retain a
name-absent Pattern-layer boundary with the peeled layer's ordering. This is a
semantic view marker, not source wildcard `_` and not an artificial child.

This is not a rule that naked Product becomes unordered: `(a, b)? = (a, b)`
is a fixed point and gains no order-insensitive matching authority. Formally,
the peel is `PatternLayer(c, B, O) -> PatternLayer(NameAbsent, B, O)`, not
`PatternLayer(c, B, O) -> Product(B)`.

`?` does not keep peeling until a target pattern is found, search for an
extractor, perform Error propagation, or convert a value into a Pattern.

The minimal sum-pattern example is `bool` (see
`return-value-extraction-and-implicit-decomposition.md` and
`static-pattern-spaces-and-extraction-chains.md`§9): logical operators return a
normal bool symbol whose Pattern carries only `if::bool | else::bool`;
`true` and `false` are ordinary bindings of those two Pattern symbols:

```text
let true  = if::bool;
let false = else::bool;
```

Each is a fresh symbol in a fresh place whose value is the corresponding Pattern
symbol's value; neither forwards the target symbol or its place
(`SymbolId(true) ≠ SymbolId(if::bool)`).
Pattern matching reads that layer directly; `bool_cond?` only requests its
one-layer top Pattern view.

`(int Vec::std)? == (int Vec::std)` — the construction value is a leaf in
ordinary value context, so `?` is idempotent.

Equality never inserts `?`. Binding and extraction do not need to insert `?` as
an enabling bridge.

This is future extraction-view semantics, not the next implementation
milestone. Early extraction-pattern work must first build the shape substrate:

```text
NormPattern / let-left material
  -> ExtractionPatternTree
  -> HoleCapture list
  -> ResolvedPatternHead list
  -> well-formedness diagnostics
```

That milestone must not execute RHS extraction, request pattern-directed
implicit `?`, recursively peel values, implement Done / residual / sum
exhaustiveness, or integrate access-tree checking.

## 4. Product Return and Non-Product Return

For product return:

```text
let P = () |> two_return;
P == (a, b);              // result is product normal form
P? == P;                  // product normal form has no shell to peel
let a, b = P;             // product binding consumes P directly
(a, b) == P;              // true
```

For non-product value `e`:

```text
let e = () |> single_return;
e? == e;                  // if e is leaf
let a, b = e?;            // error if e? is still leaf
(a, b) == e;              // false if e is not product normal form
```

For a symbol `e` whose one top Pattern shell contains product Pattern `P`:

```text
e? == P
P == e?                   // true
P == e                    // false
P A== e                   // true under named constructor / pattern A
```

`A==` is provisional notation for constructor/pattern mediated equality. It is
not ordinary value equality.

Binding and matching read `e`'s Pattern layer directly:

```text
let a, b = e              // no implicit `?` insertion or retry
let a, b = e?             // explicitly use the one-layer top-Pattern view
```

These forms may expose the same Pattern in a simple case, but they are not a
failure-and-repair protocol. Postfix `?` remains an explicit view transition,
not an extraction retry. When a top Pattern is actually peeled, the future
view retains a name-absent Pattern-layer boundary as specified above.

## 5. Compile Computes Values; Meta Carries World Authority

This narrative depends on, but does not redefine, the canonical split. The split
is about *rooting*, not about result rank:

```text
compile -> computes values; grants no root authority of its own
ordinary meta
        -> callable kind fixes P2 = meta and result classifier symbol
        -> a WellFormedMetaCall establishes root identity and
           construction navigation, not external installation
```

`compile` is value-level staging and may return any declared ordinary
PatternValue. `meta` is symbol-level staging and returns the ordinary Symbol
value of its instance; this remains within PatternValue rather than defining a
construction rank. The exact
`MetaInstanceScope`, seal order, pure-role self-root, rank-directed identity,
and formal-return rules belong solely to
`symbol-world/symbol-first-meta-construction-and-pattern-injection.md` §4.1 and
§4.3. This spine uses their results when describing value and extraction flow.

## 6. Invocation Returns an Uninstalled Value; Binding Installs It

The future invocation layer produces one of:

```text
PatternValue (including symbol)
runtime value
Residual
Diagnostic
```

The expansion/binding layer consumes the value and installs graph/world state
only when `let` creates a destination (`NamespaceDelta`, symbol binding, facet
exposure, and context-directed P1 projection of result entries). Ordinary `=`
writes an existing place; `inject` is read--extend--write over one type ref and
creates no graph member/root. Result
value/pattern entries retain `Pv:Pp`, returned Val2 objects retain their own
pair, and there is no independent `P3`. Return positions nevertheless inherit
P1 and may refine its mutability only, symmetrically with parameter refinement
of P2. For symbol construction the binding layer
must keep `pattern_owner(V)` distinct from `install_place(V)`; a binding target
does not reroot the construction's pattern owner.

The current `MetaInvocationResult` / `MetaInvocationValue` and binding APIs are
transitional transport. They do not implement the canonical result objects,
meta-instance identity/self-root validation, namespace origin, or construction
ownership.

`IdentityType` proves invocation plumbing. It does not prove final meta
construction, `MetaInstanceScopeId`, or return pure-role self-root validation.

## 6.1 Control-Flow-Local Meta Evaluation

Branch-local guarded evaluation rests on four cornerstones (see
`static-pattern-spaces-and-extraction-chains.md`§17): sum patterns for
branch-selection material, simple type check for branch-local type facts, simple
policy check for branch-local capability facts, and symbol-space construction and
lookup for branch-local names. The central invariant is that only the selected
branch may perform lookup, policy check, meta invocation, or local symbol
construction; unselected branches have no obligation of any kind.

That selected-branch rule applies after a statically selected scrutinee value
slice is known. Compile-flow projection retains the `Pp`/Pattern component of
runtime-valued symbols, and automatic require represents every
runtime-reachable branch as a pattern-guarded contract. See
`symbol-world/symbol-policy-and-compile-flow-projection.md`.

## 7. Implementation Guardrails Follow From This Spine

The implementation invariants (closed loop, no-bypass, ProductObject,
ArgProductShape, symbol/place/type-value separation, current policy metadata,
canonical `Pv:Pp`, context-directed P1/P2 elaboration, canonical
meta instance key, NamespaceDelta atomicity) are consequences of the semantic
model above, recorded in:

`spec/contracts/v0.8-meta-construction-agent-constraints.md`

`ProductObject` and `ArgProductShape` describe only the explicit user-supplied
argument product. Caller self is injected by the invocation frame into
callable-frame slot 0 and must not be added to product shape or canonical meta
instance keys. The first written formal, independent of spelling and closure
placement, is the explicit Pattern for that implicit slot; only later formals
consume `ProductObject` positions.

## Implementation Substrate Note

The connected `lang_build` invocation slice now represents:

```text
SemanticWorld
  Symbol -> heterogeneous Val2
  SemanticValue -> TypeValue -> PatternValue
  PatternValue -> ResolvedPatternScope -> associated Val2

ordinary invocation
  PreparedCallCandidate
  InvocationFrame
  complete PolicyResultEntry[]
```

An ordinary binding creates a distinct semantic Symbol/place while binding the
exact evaluated semantic value. Thus `let T: type = uint8; let U: type = T`
gives three carrier Symbols but one TypeValue Val1 and one PatternValue; it
does not reroot the Pattern owner or retain an RHS carrier as value identity.
The compatibility graph `TypeObject` now explicitly separates
`carrier_symbol_id` from `represented_type`. Source calls and already-authorized
Pattern-associated operations use different entrances and one candidate/body/
result trunk. Named associated source navigation through a rebound type value
uses `carrier Symbol -> represented TypeValue/PatternValue -> resolved Pattern
scope -> associated Symbol`; it never recovers the original carrier Symbol.

This forward-only rule now also reaches struct field classification and
extraction material. Field signatures and generated type-definition keys
consume the evaluated field `TypeValueId`; Pattern-head and constructed-value
field identity carry that TypeValue rather than the source carrier Symbol.
Compatibility graph objects may retain a carrier solely to navigate currently
installed namespace material. Thus rebinding a type value cannot perturb a
canonical struct instance or its extraction type.

The connected ordinary Pattern matcher likewise resolves written type-pattern
names forward to their evaluated type/Pattern material and compares that
identity with the argument value. The older graph-only restricted selector now
performs the same `name -> TypeObject -> represented TypeValue` step for its
bounded top-type Pattern subset; it no longer compares the actual carrier
spelling with the formal spelling. This keeps the adapter conservative without
pretending that its shallow matcher is the final PatternValue calculus.

This is a first-order connected carrier, not completion of canonical
constructor/extractor Pattern semantics. Result construction currently reuses
the registered PatternValue of the selected TypeValue; materialization place,
full Pattern shape matching, return-pattern delivery, and runtime lowering are
still incomplete.

The v0.8 build substrate represents return normal form explicitly:

```text
EvalResultNormalForm = ValuePoint(e) | Product(P)
```

The current `question_view` helper is a transitional shape-level adapter:

```text
Product(P) -> Product(P)
leaf e     -> e
non-leaf e -> exposed view
```

This helper predates the final rule and does not define postfix `?` semantics.
The canonical default is exactly one top-Pattern peel, with leaves and Pattern
normal forms as fixed points. The future exposed extraction view of a
successfully peeled top Pattern also retains a name-absent Pattern-layer
boundary and its ordering; Product fixed points do not gain such authority.

Target `struct` forms the complete immutable closure directly:
`tau = <Q_struct,V_τ>`, optionally written
`bind alpha.<Q_struct,V_τ[alpha]>`, where `Q_struct` with `Pure(Q_struct)` and
`TypeRole(Q_struct)` is the core produced during the formation event, plus any
explicitly contributed ordinary sibling values. Its mechanically generated
field/access/ref/share/write candidates are ordinary members entering `V_τ` in
that same formation event. A Symbol appears only at a subsequent
binding/install of the formed value. Those same members are exposed through
same-name associated `Val2` Symbols under `Q_struct`; the associated view does
not own a second copy. Type-as-callee uses its own `CallSpace(tau)=V_τ`;
defining-Symbol or carrier-provenance recovery is retired.
The current
substrate records part of that interface in materialized `TypeObject` metadata;
this is implementation transport, not the canonical ontology. Formal `struct`
remains graph-installation-free/binding-free even when the current invocation
path allocates registry-backed pattern material.

Pattern matching and binding read the symbol's Pattern layer directly; they do
not request implicit `?` as repair. Explicit postfix `?` only asks for the
one-layer top-Pattern view. Equality and ordinary expression evaluation do not
insert it either.

Implementation status: the next-stage `ExtractionPatternTree` / `HoleCapture`
substrate stops at Pattern-head and hole-capture well-formedness diagnostics.
It does not implement implicit `?` or extraction execution.
