# v0.6 Cross-Policy Value Transition Contract

Status: implemented `lang_build` demand-decomposition substrate and Policy
candidate-ordering prototype. This is not public frontend behavior. The
caller-supplied transition candidate adapter is transitional and is not the
final global Symbol/function-object routing architecture.

## 1. Purpose

This contract freezes the first value-policy transition slice at the
intersection of canonical `PolicyPair`, multi-entry result slicing, typed
transition demands, and Policy candidate comparison.

```text
cross-policy transition != coercion graph
cross-policy transition != type-checker conversion magic
cross-policy transition != temporary lifetime extension
cross-policy transition != global materialization
```

The compiler detects and validates a demand. The final architecture requires
the transition effect to come from a globally resolved ordinary callable; that
integration is not yet implemented by this slice.

## 2. Atomic builtin families, concrete Tnum, and literals

The first atomic builtin families (`T`) are:

```text
uint
int
float
buffer
str
```

They form `AtomicBuiltinFamily`. A family is classification material and is
not a `TypeValueId`.

Concrete numeric types (`Tnum`) are separate:

```text
NumericTypeKey {
    family: uint | int | float,
    width,
}
    -> canonical TypeValueId
```

`NumericTypeRegistry::from_core_world` connects the installed core Type symbols
`uint8/16/32/64`, `int8/16/32/64`, and `float32/64` to their canonical
`TypeValueId` projections. Additional widths can be added without growing a
family enum.

The invariant is:

```text
AtomicBuiltinFamily::Int != TypeValueId(concrete Tnum)
```

“Builtin” and “atomic builtin” are not synonyms: dependent constructors such as
`ref(T)`, `share(T)`, and `alias(T)` produce identities from another
`TypeValue`; they are not atomic. `T move == T` continues to be a type-identity
fixed point.

Normalized syntax currently exposes integer, float, and string literal kinds.
A literal retains its family, but numeric materialization also requires a
context-selected concrete `NumericTypeKey`:

```text
integer literal -> family Int   + selected concrete Tnum @ compile
float literal   -> family Float + selected concrete Tnum @ compile
string literal  -> family Str   + concrete str TypeValue @ compile
```

This slice deliberately defines no implicit default for an unsuffixed numeric
literal. Range/context/default-width selection remains a separate decision.
`uint` and `buffer` do not acquire an invented literal syntax mapping.

A literal is a value, not storage or a reference. In particular, a string
literal is a compile-stage `str` value. It is not `str ref`, a static array, or
implicit global storage.

## 3. P1 elaboration decomposes a multi-entry result

For each concrete RHS entry:

```text
P2 = P2v:P2p
DefaultP1(P2) = (P2v || P2p):P2p
```

The stage union does not manufacture a value for an absent value component.
Other typed dimensions are preserved.

P1 elaboration operates on existing `PolicyResultEntry[]` rather than
collapsing the RHS to one `PolicyPair`. For a value-bearing result it records:

```text
P1Elaboration {
    explicit/inferred origin,
    requested P1,
    existing_slices: [...],
    missing_value_demands: [...],
}
```

Projection and transition are not whole-target alternatives:

```text
requested P1
  -> project every already-existing requested slice with project_p1
  -> derive each missing requested Val1 slice
  -> create one direct PolicyTransitionDemand per missing value slice
  -> combine retained entries with produced transition entries
```

### 3.1 Omitted or identical P1

An omitted P1 defaults every result entry with `DefaultP1(P2)`. An explicit P1
equal to the available view selects the same entries. Explicit/inferred origin
remains diagnostic provenance.

### 3.2 Existing-slice projection

Every requested slice already carried by an RHS entry is selected through
`project_p1`. The resulting entry preserves its value and Pattern identities
while cropping its Policy view.

### 3.3 Missing value demands

Each missing value slice forms its own request:

```text
PolicyTransitionRequest {
    source_policy,
    target_policy: one missing Val1 slice,
    source_type,
    source_value,
    provenance,
}
```

The complete orthogonal case is:

```text
source = compile:compile
requested = (compile || runtime):compile

existing_slices =
    compile:compile with original SemanticValueId

missing_value_demands =
    compile:compile -> runtime:compile

final result =
    existing compile entry + newly produced runtime entry
```

The runtime validator sees only `runtime:compile`, never the whole
`(compile || runtime):compile` target.

### 3.4 Pure type / absent Val1

Pure types use a separate projection-only API:

```text
PolicyResultEntry<Infallible, Pattern>
    -> PureTypeP1Elaboration
```

`Infallible` makes a value identity unconstructible, and
`PureTypeP1Elaboration` has no transition-demand field. Therefore:

```text
absent:(meta || compile) -> absent:compile
    = Pattern slice only

unavailable Pattern slice
    = typed projection failure
```

A pure type cannot construct `PolicyTransitionRequest`.

## 4. Runtime value transition legality

The first frozen atomic transition changes the Val1 stage to runtime while
preserving Pattern policy:

```text
RuntimeTransitionLegal(source, missing_target)
iff
    missing_target.Pv is present at exactly {runtime}
    && Stage(missing_target.Pv) intersect Stage(missing_target.Pp) == empty
    && missing_target.Pp == source.Pp
```

Failures are typed:

```text
TargetValueNotRuntime
ValuePatternStageOverlap
PatternPolicyChanged
```

This validator is not generalized to meta/compile/seal.

## 5. Transitional candidate-algebra adapter

The current `PolicyTransitionCallable`/`PolicyBridgeBody` representation is an
intermediate prototype. It proves:

```text
caller-supplied prototype candidates
  -> hard admissibility
  -> type-input preference
  -> policy-input preference
  -> policy-output preference
  -> shared maximal-element selection
  -> unique prototype candidate or ambiguity
```

It shares only the maximal-element rule with the current ordinary overload
slice. It does **not** yet perform:

```text
global Symbol lookup
  -> heterogeneous Val2 enumeration
  -> value/type/associated () routing
  -> InvocationFrame
  -> ordinary prepared callable candidate
  -> ordinary invocation
```

Therefore this adapter must not become a second permanent callable
representation. Future integration will turn each `PolicyTransitionDemand`
into an implicit ordinary invocation of a distinguished global function family
and derive Policy comparison dimensions from ordinary candidates.

The prototype receives a direct candidate family and never feeds an output
back into candidate preparation. Thus `A -> B` plus `B -> C` never implies
`A -> C`. A selected prototype failure also cannot reopen discarded
candidates.

## 6. Candidate admissibility and preference

A prototype candidate is admissible only when:

```text
ordinary hard conditions hold
input type accepts source type
candidate input Policy intersects an available source slice
candidate output Policy covers the missing target slice
optional required output type matches
```

An output-type expectation is a hard applicability condition only. Output type
does not become ordinary type-overload preference.

For a direct transition `S -> T`, Policy preference is:

```text
InputPolicyPreference(candidate, S)
  x
OutputPolicyPreference(candidate, T)
```

The complete comparison is a product/Pareto partial order:

```text
better input + worse output => incomparable
worse input + better output => incomparable
```

All maximal candidates are retained. Declaration order is never a tiebreaker.
Delete becomes a rejection only when uniquely selected.

## 8. Explicit non-goals

This slice does not implement:

- final global Symbol/function-object bridge routing;
- a transitive implicit-conversion graph;
- complete general runtime/type overload resolution;
- implicit default/range selection for unsuffixed numeric literals;
- output-type preference;
- string-literal storage/reference magic;
- a `ref` type-checker special case;
- temporary lifetime extension;
- complete `[[global]]`/seal materialization;
- ref/share/alias lifetime/access semantics;
- meta/compile/seal transition legality;
- HIR, runtime IR, ABI, or code generation.
