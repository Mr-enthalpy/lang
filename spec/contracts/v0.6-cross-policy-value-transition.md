# v0.6 Cross-Policy Value-Transition Prototype Contract

Status: implemented `lang_build` helper substrate and candidate-ordering
prototype. This is not public language behavior and is not an end-to-end
transition implementation.

## 1. Authority and scope

This contract is an implementation delta below the existing authority chain:

```text
spec/public/
  -> canonical topic owner in spec/design/
  -> applicable existing contracts
  -> this prototype delta
```

It must not redefine ordinary binding P1, function-object P1 derivation,
symbol-first invocation, or literal lexical behavior. Those remain owned by:

```text
spec/design/symbol-world/symbol-policy-and-compile-flow-projection.md
spec/design/symbol-world/symbol-first-meta-construction-and-pattern-injection.md
spec/design/symbol-world/function-object-call-model.md
spec/design/symbol-world/type-values-places-and-alias-forwarding.md
spec/design/patterns-overload/overload-resolution-design.md
spec/public/v0.2/lexical-syntax-v0.2.md
```

The current code proves bounded data shapes, atomic Runtime-migration
validation, and
an input/output Policy partial order. It does not prove that ordinary source
initializers invoke a migration operation's ordinary callable family.

Canonical design treats a `PolicyDemand` only as consumer-origin metadata:
every consumer first asks whether the demanded Policy view already exists.
A failed complete query does not authorize arbitrary operation search. If it
accepts runtime, its runtime branch is the one currently language-authorized
constructible stage branch. The current helper implements only the ordinary
binding-P1 entry point.

## 2. Existing ordinary P1 semantics are unchanged

For ordinary binding:

```text
Gamma |- expr => PolicyResultEntry[]
selected := ProjectP1(P1, result(expr))
```

Omitted P1 retains the complete RHS result exactly:

```text
let x = expr
  -> selected = result(expr)
```

It does not use the function-object stage-lift formula. In particular:

```text
RHS = runtime:compile
omitted ordinary P1
  -> runtime:compile
```

The distinct function-object derivation remains:

```text
Stage(P1v) = Stage(P2v) || Stage(P2p)
Stage(P1p) = Stage(P2p)
```

An explicit ordinary P1 is a projection query, not an exact domain that must
be manufactured. Any non-empty projection completes ordinary P1 elaboration:

```text
source = meta:meta
query  = (meta || runtime):meta
result = meta:meta
```

No runtime transition is requested in that example. Likewise:

```text
source = compile:compile
query  = (compile || runtime):compile
result = compile:compile
```

The absent alternative is not a missing value obligation.

## 3. Binding-P1 prototype migration-preparation boundary

The helper elaborator follows:

```text
P1 omitted
  -> preserve complete RHS entries

P1 explicit
  -> selected := project_p1(P1, RHS entries)

selected non-empty
  -> identity-preserving projection

selected empty
  -> value-bearing := entries whose Val1 exists
  -> no value-bearing entry: projection failure
  -> original query does not accept runtime: projection failure
  -> otherwise:
       derive runtime-only RuntimeBranch(original query)
       slice each entry's Pp stage/domain capability
       prepare atomic Runtime migration only from eligible static entries
```

This boundary is represented by:

```text
P1Elaboration::Projected
P1Elaboration::AtomicRuntimeMigration
```

The input collection may mix value-bearing and absent-Val1 entries. No
whole-collection presence classification runs before `project_p1`; therefore a
mixed collection that succeeded under the old projection returns exactly the
same selected entries and identities. An absent entry merely lacks transition
capability.

It deliberately does not combine an existing projection with manufactured
answers for every unselected query alternative. One accepted runtime branch
may be constructed only after the complete choice projects nothing:

```text
source = compile:compile
query  = (meta || runtime):compile

ProjectP1(query, source) = empty
RuntimeBranch(query)     = runtime:compile
```

The derived internal request targets `runtime:compile`; it does not
manufacture meta.

The ordered decomposition is:

```text
Project_out o AtomicRuntimeMigration o Project_in
```

`Project_in` and `Project_out` reuse existing Policy slicing. They are not
alternative candidates competing with migration. A successful outer
projection makes candidate enumeration and migration semantically
unreachable. If migration is reached, candidate input Policy may select one
compatible static source view, and the ordinary result is sliced to the
demanded output view.

The target carried by `PolicyTransitionRequest` remains runtime-only. This is
the derived branch, not a restriction that the original P1 query must be a
runtime singleton. Candidate input/output hard adaptation projects typed
stage, presence, and Pp coordinates without fabricating a concrete
`PolicyResultEntry`. Candidate mutability is not part of that hard
intersection; it participates in actual-relative endpoint preference.

## 4. Absent Val1 is outside transition

Canonical absence remains:

```text
Pv = absent
  -> value stages = empty
  -> value mutability = empty
  -> no SemanticValueId
```

Pure Pattern/type callers may additionally use:

```text
PolicyResultEntry<Infallible, Pattern>
  -> PureTypeP1Elaboration
```

That specialized carrier exposes projection results only. The general
elaborator also accepts mixed collections, but skips every absent entry when an
empty projection reaches transition preparation. If all entries are absent,
the same typed projection failure is returned.

`PolicyTransitionRequest` has private fields and a checked constructor.
Construction rejects absent or empty-stage source value policies, a source
endpoint which contains runtime, an invalid static/Pattern-stage relation, and
a derived target which is not present and runtime-only. The source check is
about selected `Project_in`, not the complete result: a complete
`compile || runtime` result may still rematerialize from its static view when
its existing runtime branch is incompatible with another requested coordinate.
Runtime validation independently rechecks the selected endpoints.

## 5. Atomic builtin type T and concrete numeric type Tnum

The helper separates three identities:

```text
LiteralFamily
  = Integer | Float | String

AtomicBuiltinType (T lookup key)
  = Uint | Int | Float | Buffer | Str

NumericTypeKey (concrete Tnum key)
  = NumericFamily x width
```

`LiteralFamily` is syntax classification. `AtomicBuiltinType` denotes an
actual atomic builtin type; the Rust enum is a lookup key whose registry entry
is the current first-order `TypeValueId` projection of an installed Type
symbol. Requiring a concrete Tnum for a numeric literal does not redefine the
atomic numeric T members as non-types.

`NumericTypeRegistry` likewise maps a concrete numeric key to the current
first-order `TypeValueId` projection derived from an installed canonical core
Type symbol. Current `TypeValueId` is transitional projection material, not
final canonical type-value tracking/equality.

The current `main` core bootstrap provides:

```text
uint8
uint16
uint32
float32
```

The registry maps exactly those installed numeric symbols. This prototype does
not invent additional core types. Callers may extend a registry with other
first-order projections derived from already-resolved Type symbols.

An integer literal may select a signed or unsigned concrete numeric key; a
float literal may select a concrete float key. No default width, signedness,
range, overflow, or contextual-selection algorithm is frozen here.

The design target is compile-stage `str`, never `str ref`, implicit storage, or
a lifetime extension. The current core bootstrap does not install a `str` Type
symbol. The helper can form the target shape only when
`AtomicBuiltinTypeRegistry` contains a resolved `str` projection; it cannot
accept an arbitrary numeric identifier as a TypeValue. This is not yet a
core-backed implementation fact.

The helper is not called by `evaluate_initializer_best_effort`. The real
initializer evaluator still recognizes type names and restricted call sites;
standalone literals currently residualize as unsupported expressions.

## 6. Atomic Runtime migration validation

The bounded Runtime Val1 validator checks a selected atomic endpoint. Define:

```text
S = Static(source.Pv) = source.Pv - runtime

RuntimeMigrationLegal(source, selected_output)
iff
    source has a value
    && runtime is absent from source.Pv
    && S is non-empty
    && S = source.Pp
    && selected_output.Pv is present at exactly runtime
    && selected_output.Pv stages intersect selected_output.Pp stages is empty
    && selected_output.Pp = source.Pp
```

The compiler-mandated skeleton is therefore:

```text
input:  Type=T, value stage=S,       Pp=S
output: Type=T, value stage=runtime, Pp=S, presence=present
```

The validator deliberately does not require input and output value mutability
to be equal. Mutability endpoints belong to the ordinary callable, so
`const + compile -> mut + runtime` is representable for construction of a
fresh runtime object. The compiler authorizes the stage edge; it does not
synthesize the output capability. Candidate preparation does not intersect
candidate mutability with source/target mutability as a hard domain check.
Opposite const/mut Patterns remain admissible and are ordered by the existing
actual-relative ordinary rule:

```text
const actual/demand: const > unspecified > mut
mut actual/demand:   mut > unspecified > const
```

The current prototype reuses the ordinary rank helper for singleton
source/target mutability. Stage, presence, Pp capability, Type, and structural
applicability remain hard endpoint checks.

The default four-member transport fixture now models complete ordinary
callable Policies rather than direct migration-edge Policies:

```text
ordinary input formal P2:
  (compile || runtime):compile

ordinary complete result P2:
  (compile || runtime):compile

mutability members (output <- input):
  const <- const
  const <- mut
  mut   <- const
  mut   <- mut
```

For an atomic request, `Project_in` selects the compile input view and
`Project_out` selects the runtime result view. The complete ordinary P2 is not
rewritten into `compile -> runtime`.

Pattern-side Policy capability does not migrate to runtime. Equality of the
selected Pp capability is not an instruction to copy the source Pattern
object; an eventual ordinary invocation owns result Pattern construction.

Typed failures are:

```text
SourceValueAbsent
SelectedInputContainsRuntime
SourceStaticValueStageDomainEmpty
SourceStaticPatternStageMismatch
TargetValueNotRuntime
ValuePatternStageOverlap
PatternPolicyChanged
```

This is not a general meta/compile/seal transition rule.

For pair P1 `Qv:Qp`, demand preparation first intersects `Qp` with the source
Pattern-Policy stage/domain capability. Empty intersection makes that source
entry ineligible; migration cannot repair the Pattern side. This Policy
slicing is not Pattern extraction, PatternValue projection, `?`, PatternHead
navigation, or a PatternRoot/PatternScope change.

The current execution carrier is intentionally named as prototype material:

```text
PrototypeTransitionResultCarrier {
  entry: PolicyResultEntry<SemanticValueRef, Pattern>
  source_value
  provenance
}
```

The caller supplies the complete fixture result entry. This proves only that
the helper can carry ordinary-result-shaped data. It does not establish final
TypeValue/PatternValue/Pattern-owner/constructor-extractor coherence, and a
fixture such as `"ref-pattern"` is not evidence that canonical Pattern result
construction is wired. The prototype nevertheless keeps two Policy facts
distinct:

```text
ResolvedPolicyBridge.complete_result_policy
  = the selected callable's complete ordinary P2

ResolvedPolicyBridge.validated_output_endpoint
  = runtime-stage endpoint used by prototype validation/Bp comparison
```

`invoke_resolved_policy_bridge` constructs its fixture entry with
`complete_result_policy`; `assemble_transition_results` performs the separate
output projection. The carrier therefore no longer conflates the ordinary
result `Ro` with the demanded view `Rd = Project_out(Ro)`. When a uniquely
selected callable declares an opposite result-mutability Pattern, the
validated endpoint can still exist for ordering while final `Project_out` may
fail; that failure does not reopen selection.

## 7. Candidate-ordering prototype

`PolicyTransitionCallable` and `PolicyBridgeBody` are transitional test
carriers supplied directly by the caller. They prove:

```text
hard structural/type/input/output-query admissibility
  -> fallback suppression
  -> endpoint-only Policy product fixture:
       transition-input endpoint fit
         (including actual-relative input mutability)
       x transition-output endpoint fit
         (including actual-relative output mutability)
  -> ordinary input-type predecessor fixture
  -> Pattern-specificity B3 fixture
  -> shared maximal-element selection
  -> unique candidate, delete rejection, or ambiguity
```

Canonical `Bp'` is one product over ordinary Bp coordinates plus both endpoint
coordinates. The Rust prototype has no ordinary Bp carrier and proves only the
endpoint-coordinate product and its placement before the B3 stand-in. Its
endpoint-only maxima helper is private because it cannot be sequentially
composed with old Bp maxima. Crossed input/output endpoint advantages remain
incomparable. Declaration order is not a tiebreaker. Output type is a hard
expectation only and does not become ordinary return-type preference.
Namespace visibility and export-root metadata are rejected rather than ranked.
Presence specificity remains local to these endpoint coordinates and is not a
general Policy overload rule. Candidate outputs are not recursively fed back
into selection, so no migration graph or transitive search exists. A
selected-body failure cannot reopen the discarded candidate set.

Current source language cannot construct a fallback candidate role, so current
ordinary calls retain `Af = A` and the old `A -> Bp'` pipeline. The Rust
prototype carries fixture-only fallback metadata to test the already-fixed
semantics of a possible future fallback strategy:

```text
A  = FullyAdmissible(...)
Af = SuppressFallback(A)
Bp' consumes Af
```

When/if that future strategy is present and `A` contains any admissible
non-fallback candidate, all fallback candidates are removed; otherwise
fallback candidates remain. An admissible non-fallback `delete` counts and
therefore suppresses fallback permanently. A later delete rejection cannot
retry fallback. The Rust marker remains fixture metadata; the surface spelling
and final ordinary candidate storage are not frozen here.
The combined transport fixture marks the complete four-member default
mutability relation as fallback, then admits one finer ordinary `delete` only
for one structural/require region. That region suppresses its default member;
the other input/output cells continue to be filled by the fallback quartet.
The fixture uses ordinary hard admissibility to delimit the fine region:
mutability remains an actual-relative Bp' coordinate, not hard compatibility.

`project_transition_policy_domain` remains a capability-domain projection
helper for stage/presence/Pp-oriented fixture tests. It is not used to decide
migration-candidate mutability admissibility. The resolver instead projects
the hard endpoint coordinates separately and sends candidate mutability to the
same actual-relative preference rule used by ordinary Bp. A candidate whose
input and/or output mutability is opposite is therefore not removed merely for
that mismatch.

Candidate output Type must equal the source Type in this atomic migration
prototype. A failed Type/Pattern structural applicability judgment cannot be
repaired by searching `ref`, `share`, `alias`, or another structure-changing
operation. Those operations, when explicitly required by language semantics,
remain separate ordinary function-object calls.

Callable-declared endpoint mutability is not structural repair. A generic
`const compile -> mut runtime` candidate and a structurally specific `T ref`
delete candidate may expose the same endpoints; the endpoint product ties,
the B3 stand-in selects the more specific Pattern, and the unique delete
rejects the operation.

Outer candidate qualification is typed:

```text
BridgeQualification
  = Available(resolved bridge)
  | RejectedByDelete
  | Missing
  | Ambiguous
```

Only `Available` admits the outer candidate. A unique delete winner is a
specific rejection, not migration availability; the failure kind remains
available for diagnostics if every outer candidate is excluded.

This prototype does not perform:

```text
ResolveSymbol
  -> enumerate heterogeneous Val2
  -> obtain value TypeValue
  -> resolve associated ()
  -> build InvocationFrame with caller/self in slot 0
  -> prepare ordinary callable candidates
  -> invoke selected ordinary function object
```

`PolicyBridgeBody::UserCallable(SymbolId)` records an intended symbol only; the
prototype does not invoke it. The carrier must not become a second permanent
callable representation.

Canonical invocation does not introduce a transition callable ontology or
freeze one universal global transition Symbol. The language-authorized atomic
migration eventually selects an ordinary callable family. Separately selected
mechanical `ref`, `share`, or `alias` operations may route to their own
ordinary callable families and may change structure.

The current staged prototype proves only:

```text
fallback suppression
  -> transition endpoint Policy product fixture
  -> ordinary input-type predecessor stand-in
  -> Pattern-specificity B3 stand-in
```

It does not yet combine the real ordinary `Bp` coordinates with endpoint
coordinates or execute the complete B1..B6 pipeline.

## 9. Explicitly not implemented

- ordinary initializer/binding integration;
- migration-operation-to-Symbol/Val2/associated-`()` callable-family routing;
- ordinary `InvocationFrame` construction or function-object invocation;
- a world-backed `SemanticValueId` allocator;
- implicit numeric literal type selection;
- runtime lowering or backend materialization;
- `ref` storage construction and `share`/`alias` composition;
- `[[global]]` seal scanning;
- lifetime extension or lifetime-driven overload reopening;
- a transitive coercion/conversion graph;
- residual IR/object representation, the physical residual `InvocationFrame`,
  the maximal-static-evaluation algorithm under effects, precise effect
  sequencing, continuation ABI, or capability/effect integration. The core
  mixed-stage meaning—existing stage slices, phase-dependent readability,
  early evaluation of readable dependencies, residualization of runtime
  dependencies, and continuation of the same resolved invocation—is already a
  design invariant rather than an open question.
