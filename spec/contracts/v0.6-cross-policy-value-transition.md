# v0.6 Cross-Policy Value Transition Contract

Status: implemented `lang_build` semantic substrate and tested vertical slice.
This is not public frontend behavior and does not claim a complete general
overload resolver, evaluator, lifetime system, or runtime backend.

## 1. Purpose

This contract freezes the first value-policy transition slice at the
intersection of canonical `PolicyPair`, function objects, ordinary candidate
selection, and phase-aware evaluation.

```text
cross-policy transition != coercion graph
cross-policy transition != type-checker conversion magic
cross-policy transition != temporary lifetime extension
cross-policy transition != global materialization
```

The compiler detects and validates a request. The transition effect comes from
the selected callable implementation.

## 2. Atomic builtin types and literals

The first atomic builtin type identities are:

```text
uint
int
float
buffer
str
```

They form the typed `AtomicBuiltinType` set and are supplied through an explicit
`AtomicBuiltinTypeIds` bootstrap handoff; the literal evaluator never invents
numeric identities. This slice deliberately does not alter the current default
core-mount conflict/shadowing rules to install new short names, because current
fixtures may declare local names such as `int`. Persistent namespace
installation is a separate bootstrap integration task.

“Builtin” and “atomic builtin” are not synonyms: dependent constructors such as
`ref(T)`, `share(T)`, and `alias(T)` produce identities from another
`TypeValue`; they are not atomic. `T move == T` continues to be a type-identity
fixed point.

Normalized syntax currently exposes integer, float, and string literal kinds.
Their semantic entry is:

```text
integer literal -> int value   @ compile
float literal   -> float value @ compile
string literal  -> str value   @ compile
```

`uint` and `buffer` are registered atomic type identities but do not acquire an
invented syntax mapping in this slice.

A literal is a value, not storage or a reference. In particular:

```text
"abc" : str @ compile
```

It is not `str ref`, a static array, or implicit global storage. Any later
storage/reference object is produced by an ordinary callable.

## 3. P1 elaboration makes two orthogonal decisions

For one concrete RHS result pair:

```text
P2 = P2v:P2p
DefaultP1(P2) = (P2v || P2p):P2p
```

The stage union does not manufacture a value for an absent value component.
Other typed dimensions are preserved.

P1 elaboration records:

```text
effective Policy + explicit/inferred origin
optional existing-slice projection
optional PolicyTransitionRequest
```

Projection and transition are not variants of one either/or enum. Projection
answers which identity-preserving RHS slices are already available. Transition
answers whether a callable must produce a missing target value. They are
different dimensions, triggered by different facts, and a transition
candidate may select an existing input slice before performing its value
transition.

### 3.1 Identity

An omitted P1 uses `DefaultP1(P2)`. An explicit P1 equal to that pair has the
same semantic result, while explicit/inferred origin remains diagnostic
provenance.

### 3.2 Existing-slice projection

If an explicit target is already an identity-preserving slice of the RHS
result, P1 projects that existing view:

```text
source carries compile || runtime : compile
target requests runtime : compile
=> existing_slice = Some(runtime:compile)
=> transition = None
```

No bridge callable runs and no new semantic value is created.

This pair-level classification and `project_p1` over multiple result entries
are complementary forms of existing-slice selection. Multi-slice projection is
not deprecated and is not a transition fallback.

### 3.3 Transition request

A target that cannot be obtained as an identity-preserving slice forms:

```text
PolicyTransitionRequest {
    source_policy: DefaultP1(P2),
    target_policy: explicit P1,
    source_type: TypeValueId,
    source_value: SemanticValueId,
    provenance,
}
```

For example, a compile-only value requested as runtime requires a transition.
Normalized AST does not elaborate or resolve it.

The bridge's input-policy check may itself select an identity-preserving slice
from a multi-slice source. For example, a `compile:compile` input callable can
consume the compile slice of `(meta || compile):compile` and then produce a
runtime value. That input projection and the requested value transition both
occur; neither substitutes for the other.

## 4. Runtime value transition legality

The first frozen atomic transition changes the Val1 stage to runtime while
preserving Pattern policy:

```text
RuntimeTransitionLegal(source, target)
iff
    target.Pv is present at exactly {runtime}
    && Stage(target.Pv) intersect Stage(target.Pp) == empty
    && target.Pp == source.Pp
```

Failures are typed:

```text
TargetValueNotRuntime
ValuePatternStageOverlap
PatternPolicyChanged
```

This validator is not generalized to meta/compile/seal. Future transitions may
be Val1-only, Pattern-only, or coupled.

## 5. Callable bridge adapter

`PolicyBridge` names a distinguished semantic operation/family, not a second
invocation subsystem. A direct request:

```text
resolve supplied callable family
  -> ordinary hard admissibility
  -> type-input preference
  -> policy-input preference
  -> policy-output preference
  -> shared maximal-element selection
  -> unique callable or ambiguity
  -> ordinary invocation
```

The adapter uses the same maximal-element helper as the existing
phase/mutability overload slice. It receives a direct candidate family and
never feeds an output back into candidate preparation. Consequently:

```text
A -> B and B -> C do not imply A -> C
```

Composition must be written inside a callable implementation.

The minimal builtin body is ordinary value copy:

```text
compile value T -> runtime value T
```

It preserves type, Pattern policy, and value contents while producing a new
runtime value identity. `ref` fixtures enter through the same callable adapter;
const materialization is a non-delete body and mut materialization is a normal
selected-delete rejection. Full storage/global/seal lowering is not part of
this slice.

## 6. Fully admissible boundary

A direct transition callable is fully admissible only when:

```text
ordinary hard conditions hold
input type accepts source type
candidate input Policy intersects an available source slice
candidate output Policy covers required target Policy
optional required output type matches
```

An output-type expectation is a hard applicability condition only. Output type
does not become ordinary type-overload preference.

Bridge availability may be used while forming an outer callable's
`FullyAdmissible` status. Once a winner has been selected, invocation/lowering
receives only that resolved callable. It cannot reopen the discarded candidate
set.

## 7. Bidirectional Policy preference

For a transition `S -> T`, candidate Policy preference is:

```text
InputPolicyPreference(candidate, S)
  x
OutputPolicyPreference(candidate, T)
```

Each component prefers a narrower admissible Policy domain matching the
required point/view. Input admissibility may first select an existing source
slice; output admissibility must cover the complete requested target. The
complete comparison is a product/Pareto partial order.

```text
better input + worse output => incomparable
worse input + better output => incomparable
```

All remaining maximal candidates are reported as ambiguity. Declaration order
is never a tiebreaker. Delete remains an ordinary candidate and becomes a
rejection only when uniquely selected.

Policy output preference is specific to the known target Policy of a
transition. It does not add return-type-driven preference to ordinary type
overload resolution.


The current older initializer/meta adapter continues to use its existing
multi-entry `project_p1` path. End-to-end migration of every initializer and
namespace consumer to the new transition carrier is an integration task, not a
reason to collapse projection and transition into one mechanism.

## 9. Explicit non-goals

This slice does not implement:

- a transitive implicit-conversion graph;
- complete general runtime/type overload resolution;
- output-type preference;
- string-literal storage/reference magic;
- a `ref` type-checker special case;
- temporary lifetime extension;
- complete `[[global]]`/seal materialization;
- ref/share/alias lifetime/access semantics;
- meta/compile/seal transition legality;
- bridge-failure backtracking;
- HIR, runtime IR, ABI, or code generation.
