# v0.8 Symbolic Construction Values and Extraction Interfaces

**Status: Transitional v0.8 construction/extraction contract. Not current public
language behavior.** Its extraction-view and current implementation-substrate
sections remain useful. Its former formal `r = ...` versus `r === ...`
meta-return model is superseded by
`spec/design/symbol-world/symbol-first-meta-construction-and-pattern-injection.md`.
Namespace-origin and construction-unit ownership are specified by
`spec/design/symbol-world/symbol-construction-units-and-namespace-origin.md`.
Canonical `Pv:Pp`, contextual P1/P2 elaboration, seal visibility, and
compile-flow projection are
specified by
`spec/design/symbol-world/symbol-policy-and-compile-flow-projection.md`.

This document depends on the extraction-view model defined in
`spec/design/patterns-overload/return-value-extraction-and-implicit-decomposition.md`.

The v0.8 semantic spine is defined in
`spec/design/v0.8-semantic-spine.md`. This document is the detailed
construction-value chapter of that spine.

Three axioms:

1. An evaluation returns one result object whose normal form is `e` or `P`.
2. `compile` computes values and grants no root authority of its own; ordinary
   `meta` is static evaluation plus authority over a navigable
   `MetaInstanceRoot`. Within the ordinary-meta domain:

   ```text
   P2(F) = meta
     <=> EstablishNavigableMetaInstanceRoot(MetaInstance(F, Norm(args)))
   ```

   Neither statement fixes the declared return shape or assigns a generic root
   rule to privileged built-ins.
3. Extraction is a view transition, not call-history inversion.

## 1. Purpose

A name/path resolves symbol-first and then projects a namespace, type, or
heterogeneous value facet. Compile-time computation and symbol construction are
separate capabilities:

```text
compile -> ordinary PatternValue, with root conservation and no root authority
ordinary meta
        -> ordinary PatternValue, plus authority to establish and seal one
           navigable MetaInstanceRoot M
privileged builtin
        -> ordinary PatternValue under its member-specific owner rule
```

The returned *shape* is whatever the callable's `ReturnShape` declares in every
case; a symbol value is an ordinary `PatternValue` and not a separate result rank.
The canonical statement of both laws is
[`../design/symbol-world/symbol-first-meta-construction-and-pattern-injection.md`](../design/symbol-world/symbol-first-meta-construction-and-pattern-injection.md)
§4.1. Everything this document calls `SymbolConstructionValue` is the **current
implementation carrier** for the multi-member return of a meta construction, not a
result ontology and not a rule about what `meta` may return.

Therefore the implementation must distinguish at least:

```text
computed PatternValue
computed TypeValueId projection
uninstalled meta-construction carrier (current substrate: SymbolConstructionValue)
declaration binding target
installation PlaceId
extraction-facing pattern interface
```

`TypeValueId` is only a derived first-order type-value projection material. It
is not a symbol, binding source, installation place, construction identity, or
type-definition identity. There is no declaration alias forwarding and no
alias-member construction event; a member that must observe an external object
holds a borrow view (`ref` / `share`), which is an ordinary value.

## 2. Symbol Constructions Are Values

An expression such as:

```text
(uint8 Vec::std)
```

is a value. Its value is the construction expression itself:

```text
value((uint8 Vec::std)) = (uint8 Vec::std)
```

This is consistent with ordinary type values:

```text
let t = uint8
value(t) = uint8

let t = (uint8 Vec::std)
value(t) = (uint8 Vec::std)
```

`(uint8 Vec::std)` is simultaneously:

```text
a meta-construction carrier value (current substrate: SymbolConstructionValue)
a symbol-rank construction result
material that may carry a type facet / TypeValueId projection
material that may expose an extraction interface after binding
```

The implementation must not treat this as a mere erased alias for its argument.
A generated symbol construction is not automatically a declaration alias for
the argument from which its facet material was computed.

## 3. Call, Construction, and Extraction

Construction and extraction may be isomorphic. A value produced by a constructor
may expose an extraction interface that recognizes the corresponding constructed
shape.

Call and extraction are not isomorphic. A call returns a result object whose
normal form is `e` or `P`. Extraction works on the returned value's static
pattern space, not on the call target, not on the call history, and not on the
internal computation path of the callable.

The following distinction must be preserved:

```text
call          -> returns a result object with normal form e or P
construction  -> gives a non-product returned value a construction shape
extraction    -> operates on the returned value's extraction-facing pattern space
```

A call may return a construction. A call may also return product normal form.
Neither case licenses extraction through call history.

## 4. Meta Bodies Use Ordinary Block Return Semantics

A compile/meta-function body is an ordinary block for result-consumption
purposes.

The body returns by the same rule as every other block: an otherwise unconsumed
final expression is the current block result. Therefore:

```lang
let id = (self, t: type): compile -> r: type => {
    let r = t;
    r;
};
```

does not use a special compile-return form. The final expression `r` is simply
the result of the callable body block. A meta body uses the same block-result
rule, but its return construction must also satisfy the meta type self-root
invariant below.

For final symbol-first semantics, formal meta return material is the
construction-effect family on the return symbol: `let r = expr;` adds a fresh
member, `r = expr;`
writes to an existing target (the concrete write algebra is not fixed
by this contract; the current implementation is a placeholder overwrite
scaffold), and `r;` delivers the construction. What is final here is the *family
split* (create / write / deliver are distinct events); the spellings
are the current `let`-only compatibility encoding pending expression-level
`=` — the settled orthogonal target remains `let` creates, `=` writes,
return events deliver. The former
reading of `r === ...` as a second formal return category and the interim
single-form `r = ...` reading are both superseded, and there is no fourth
alias-member event.

This uses the ordinary symbol-first value-binding rule. When the right side is a
path, the evaluator resolves its symbol and reads the value/facet carried by
that symbol. For `compile`, the value may be returned directly. For `meta`, the
value becomes construction material subject to facet and root validation.

There is no declaration-layer aliasing operation. `let a = b;` binds a fresh
symbol in a fresh place carrying `b`'s value:

```text
SymbolId(a) ≠ SymbolId(b)
PlaceId(a)  ≠ PlaceId(b)
Value(a)    =  Value(b)
```

The same holds inside a meta body: a member is created by `let`, written by `=`,
and nothing forwards an external symbol's material into it.

## 5. Symbol Shielding

Meta construction shielding, canonical argument identity, the equation between
an ordinary-meta result symbol and its `MetaInstanceScope`, the lexical role of return slot `r`,
and the conditional type self-root invariant are defined only in
`spec/design/symbol-world/symbol-first-meta-construction-and-pattern-injection.md`.

This transitional contract requires current transport to avoid exposing an
internal return-slot spelling as final identity and to keep value equality
separate from `SymbolId` / `PlaceId`. It does not independently redefine the
future construction object or repeat its legal/illegal examples.

The current Rust `GeneratedConstructionValue`, `ForwardedValue`, and
`GeneratedTypeDefinitionValue` variants remain transitional transport. They are
not the final public return-rank taxonomy.

## 6. Return Slot Names Are Internal

This is invalid:

```lang
meta+ runtime let id = (self, t: type): meta -> t => {
    t;
};
```

The parameter name `t` and the return slot name `t` collide. The return slot must
have its own binding name. The external construction identity is determined by
the callee, rank-directed canonical arguments, build identity, and construction
origin, not by the internal return-slot spelling.

## 7. Rank Annotation After Symbol Binding

After symbol binding, rank annotations split into two semantic classes.

### 7.1 Hole-Bearing Rank Annotations Are Extraction Forms

Example:

```lang
let <T: type> val: T Vec::std = ...
```

Here the annotation contains a hole name. The annotation is therefore an
extraction expression over the rank annotation. It belongs to the extraction side
of the call / construction / extraction correspondence.

The annotation attempts to extract `T` from the rank/type structure of `val` by
using the extraction interface exposed by the constructed value.

This is not merely a Boolean assertion. It is a binding extraction over a static
rank pattern.

### 7.2 Hole-Free Rank Annotations Are Assertions

Example:

```lang
let val: uint8 Vec::std = ...
```

Here the annotation has no hole name. The annotation is therefore a rank
assertion of the form:

```text
target : annotation
```

The judgment evaluates whether the target satisfies the annotation:

```text
target : annotation == true   if the annotation holds
target : annotation == false  if the annotation does not hold
```

In this form, `annotation` belongs to the call side of the call / construction /
extraction correspondence, not to the extraction side.

Thus the following two surface forms must not be normalized into the same
semantic object:

```lang
let <T: type> val: T Vec::std = ...
let val: uint8 Vec::std = ...
```

The first is extraction-bearing. The second is assertion-bearing.

## 8. Pattern-Layer Access and Postfix `?`

A `Val1` leaf is not a `Pattern`; both are layers of the same symbol flow.

Pattern matching may read a symbol's Pattern layer directly. Postfix `?` is an
explicit one-layer top-Pattern view, not a prerequisite for matching:

```text
leaf? = leaf
P? = P
TopPattern(P)? = P
```

The last equation describes only the exposed resident. In the future
extraction model, a successful top-Pattern peel retains an anonymous
Pattern-layer boundary and its ordering:

```text
PatternLayer(c, B, O)? = PatternLayer(_, B, O)
```

It does not become `Product(B)`. An order-insensitive named Pattern body
therefore remains order-insensitive for the extraction consuming the peeled
view, while `P? = P` does not grant a naked Product any such authority.

This does not make leaves and patterns interchangeable. Pattern-side names do
not fall back to ordinary value/function lookup; extraction-pattern bare names
walk the established Pattern-parent chain through
`OwnNavigation = Absent` and stop at the nearest `Explicit(path)` or
`ImplicitGlobal` anchor. A root with omitted navigation is
`ImplicitGlobal`, never `Absent`; explicit subject navigation bypasses parent
completion.

This matters for compile-time identity computations. For example:

```lang
let id = (self, t: type): compile -> r: type => {
    let r = t;
    r;
};
```

`(uint8) |> id` may compute the `uint8` value, but extraction does not
automatically inspect the call history. Extraction sees only the value's exposed
static pattern space.

Attempting to extract the computed value as an `id` construction may fail for
the simplest reason:

```text
result((uint8) |> id) == uint8
```

The exposed pattern value is `uint8`, not an `id`-shaped pattern value. A meta
type construction cannot use this identity behavior to bypass its
ordinary-meta `MetaInstanceScope` self-root invariant. Symbol construction
identity is a separate question from ordinary value binding, and neither
involves place forwarding.

## 9. Product Return Normal Form

Product return is not a separate return mechanism and it is not an outer wrapper
around a product. An evaluation returns one result object whose normal form may
be `e` or `P`.

The structural distinction is:

```text
e      -> ordinary non-product value point
P      -> product value / product normal form
```

Returning one expression value returns `e`:

```text
return e => e
```

Returning a product returns `P` directly:

```text
return (e1, e2) => P(e1, e2)
```

For:

```lang
let P = () |> two_return;
```

if `two_return` returns product normal form `(a, b)`, then:

```text
P == (a, b)
P? == P
let a, b = P
(a, b) == P
```

For a non-product value `e`:

```text
e? == e             // if e is leaf
let a, b = e?       // error if e? is still leaf
(a, b) == e         // false if e is not product normal form
```

For a non-leaf construction value `e` with an exposed product view:

```text
e? == P
P == e?             // true
P == e              // false
P A== e             // true under named constructor / pattern A
```

`A==` is provisional notation for constructor/pattern mediated equality. It is
not ordinary value equality.

The following invariants are contract-level:

```text
1. `?` does not inspect call history;
2. `?` is not recursive — its default erases one peelable top Pattern name
   while retaining an anonymous Pattern-layer boundary and its ordering; a
   Product fixed point gains no order-insensitive authority;
3. product normal form satisfies P? = P;
4. binding and extraction read a symbol's Pattern layer directly and do not
   insert implicit `?`;
5. value equality never inserts `?`;
6. named extraction is not bare product extraction;
7. product matching consumes P in the pattern matcher;
8. only the selected branch of a guarded sum-pattern expression may perform
   lookup, policy check, meta invocation, or local symbol construction;
   unselected branches have no obligation of any kind.
```

## 10. Contract-Level Extraction Invariants

Product-return and extraction-view behavior is specified by
`spec/design/patterns-overload/return-value-extraction-and-implicit-decomposition.md`.

The fully named Pattern-body navigation-map/ordered-layer rule and
symbol-to-value-to-map lookup equation are owned by the canonical symbol-first
note and the pattern-space/extraction design. This contract only requires
transitional extraction interfaces to keep symbol carriers distinct from the
values they expose.

Next-stage boundary: implicit pattern-directed `?` is not part of the early
`ExtractionPatternTree` / `HoleCapture` substrate. The next target is:

```text
NormPattern / let-left material
  -> ExtractionPatternTree
  -> HoleCapture list
  -> ResolvedPatternHead list
  -> well-formedness diagnostics
```

It must not execute RHS extraction, request pattern-directed implicit `?`,
recursively peel values, implement Done / residual / sum exhaustiveness, or
integrate access-tree checking.

## 11. Implementation Requirements

Before the final compile/meta construction model can be called implemented, the
invocation result layer must be able to distinguish at least:

```text
PatternValue
runtime value / Residual
Diagnostic
```

and, independently of that rank, whether the invocation established and sealed a
meta root. The meta-construction carrier (current substrate:
`SymbolConstructionValue`) is a representation of a multi-member `PatternValue`
return, not a fourth case of this list.

A binding layer must also keep these roles distinct:

```text
returned value / construction value
namespace delta to install
declaration binding target
installation PlaceId
resolved pattern owner
extraction-facing pattern interface
canonical result pairs retained on value/Pattern entries
binding-context P1 projection without rerooting construction identity
independent policy pairs on returned Val2 objects
```

An ordinary meta construction with a type facet must additionally preserve:

```text
canonical ordinary-meta MetaInstanceScope
root_pattern_scope(TypeFacet) = MetaInstanceScope
NamespaceOrigin
SourceConstructionUnit / MetaConstructionUnit owner
```

`compile` does not create the first object and is not subject to the meta type
self-root check.

The following collapse is forbidden:

```text
meta-construction carrier(args, callee) -> TypeValueId(argument)
```

The formal return slot must not encode generation versus forwarding by choosing
between `=` and `===`; that old split is superseded.

Final formal meta return uses only `r = ...` to populate construction material.
There is no declaration-layer aliasing counterpart: ordinary binding always
allocates a fresh symbol and place.

A primitive identity proof path may demonstrate graph-resolved meta-call
plumbing, candidate preparation, or cache-key formation. It must not be used as
evidence that `PatternValue`, meta root establishment, resolved pattern scope,
meta return type self-root validation, or binding-independent `struct`
ownership has been implemented.

## 11.1 PatternHeadId Materialization Loop

The current v0.9 construction substrate uses `PatternHeadId` for constructed
pattern/value heads.

```text
ConstructorHead::Owner(owner_head)
ConstructorHead::Field(owner_head, field_head, field metadata)
ConstructorHead::Generated(construction_instance_id, generated_head)

ConstructedValue::Owner(owner_head, payload)
ConstructedValue::Field(owner_head, field_head, field metadata, payload)
ConstructedValue::Leaf(MetaInvocationValue)
```

The display spelling of a head is diagnostic/dump material only. Equality is
semantic:

```text
Owner:
  owner_head equal
  payload semantic_eq

Field:
  owner_head equal
  field_head equal
  field metadata equal
  payload semantic_eq

Leaf:
  MetaInvocationValue::semantic_eq
```

The one-step `?` behavior remains unchanged:

```text
Owner? -> payload
Field? -> payload
Leaf?  -> Leaf
```

This is an identity + reconstruction substrate. It is not full extraction
execution, recursive `?`, pattern-space algebra, layout, borrow/access-tree,
or lowering.

The substrate is connected to the current `struct` type-definition
materialization boundary. Formal `struct` invocation uses the shared
`TypeMaterializationState.pattern_heads` registry and returns a
`GeneratedTypeDefinitionValue` with generated-fallback pattern-head material:

```text
GeneratedTypeDefinitionValue.pattern_heads.owner_head
GeneratedTypeDefinitionValue.pattern_heads.field_heads
GeneratedFieldDefinition.pattern_head
```

Binding that value into the namespace graph preserves already attached
provisional owner/field heads. If cache transport stripped them, binding restores
them only under the anonymous `GeneratedTypeDefinition(type_definition_id)`
fallback. The projected `TypeObject`, `TypeField`, extraction interface, and
generated field-function payloads carry those identities; the destination path
does not select a replacement owner.

Formal `struct` invocation currently derives a fallback owner head from the
generated type-definition identity:

```text
formal struct invocation
  -> GeneratedTypeDefinitionValue
  -> PatternMaterializationContext::GeneratedTypeDefinition { type_definition_id }
  -> owner PatternHeadId
```

It preserves generative type-definition identity and registry continuity. It is
graph-installation-free and binding-free. Target semantics are referentially
pure; the current registry-backed allocation is non-semantic implementation
bookkeeping and may affect storage/cache mechanics without becoming an
observable language effect.

PR #94 adds an explicit attachment helper whose categorical context supports
generated, global, namespace, and local origins. Those categories are low-level
registry/test substrate; the helper is doc-hidden and is not a stable external
owner-construction API. Ordinary binding does not derive them from its target.
The local category exists as helper substrate but full local Self-frame lowering
is not wired. The final rule remains:

```text
struct pattern owner
  = input pattern navigation + ambient ResolvedPatternScope

binding target
  = installation PlaceId only
```

Binding the construction must not reroot pattern identity. The final
`PatternScopeId`, `MetaInstanceScopeId`, meta return type self-root check,
symbol facets, complete `compile`/`meta` split, functional `inject`,
`NamespaceOrigin`, construction-unit ownership, physical contribution
authority, cross-file reopening diagnostics, and explicit sum API are not
implemented.

`MetaInstanceCache` does not cache concrete `PatternHeadId` assignments. For
generated type definitions, cached entries retain replayable identity and
field-signature material only. A cache hit replays the pattern-head
materialization step in the caller's current `TypeMaterializationState` before
returning the value. Therefore a returned `GeneratedTypeDefinitionValue` and
the current registry remain consistent:

```text
lookup_child(value.pattern_heads.owner_head, field_name) == field_head
```

Compatibility wrappers that internally allocate a temporary
`TypeMaterializationState` do not provide registry continuity. They remain
valid for standalone invocation/binding tests, but source build paths use the
stateful entry points. The current source build main path calls the stateful
early-expansion entry point owned by `CompilationWorld`, not the standalone
wrappers.

The registry APIs used by this boundary are conflict-aware. Duplicate explicit
paths or duplicate field names under the same owner cannot silently overwrite
previous heads. The restricted resolver also treats `PatternExpectation` as a
real boundary: `AutoName` is accepted only for extraction-child lookup in this
slice, while explicit navigation resolves through the explicit path table and
never falls back to the current extraction scope.

## 12. Minimal Test Obligations

Before `(T Vec::std)` or `(A, B Pair::std)` is called complete, future semantic
tests must protect the capability/rank split rather than the obsolete formal
return-operator split.

Compile-time type-value computation:

```lang
let id_value = (self, t: type): compile -> r: type => {
    t;
};

let T: type = (uint8) |> id_value;
```

Expected:

```text
type_value(T) == type_value(uint8)
symbol(T) and place(T) remain declaration-specific
no type symbol is installed by compile invocation itself
```

Illegal identity-style meta type construction:

```lang
let BadIdentity = (self, t: type): meta -> r: symbol => {
    let r = t;
    r;
};

let BadUint8 = (self, t: type): meta -> r: symbol => {
    let r = uint8;
    r;
};
```

Expected:

```text
both constructions are rejected if the assignment would establish TypeFacet
external PatternValue root does not equal the canonical MetaInstanceScope
neither form is reinterpreted as place forwarding
```

Legal self-rooted meta symbol construction:

```lang
let Box = (self, t: type): meta -> r: symbol => {
    let r = (t inner) |> struct;
    r;
};

let T = (uint8) |> Box;
```

Expected:

```text
formal invocation returns an uninstalled pattern value
root_pattern_scope(type_facet(return symbol)) = (uint8 Box)
complete pattern = (uint8 inner::(uint8 Box))::(uint8 Box)
binding installs at place(T)
binding target does not reroot the meta result type
```

Ordinary binding behavior requires its own declaration-layer test:

```lang
let T = uint8;
```

This allocates a fresh symbol and a fresh place carrying `uint8`'s value; it
forwards nothing and is not a formal meta return.

Product-return distinction (see also
`spec/design/patterns-overload/return-value-extraction-and-implicit-decomposition.md`):

```lang
let e = () |> single_return;
let a, b = e?;        // ERROR unless e? exposes product normal form
let a, b = e;         // ERROR unless e's Pattern directly matches the product

let P = () |> two_return;
let a, b = P;         // valid: P is product normal form
P? == P;              // true
(a, b) == P;          // true when P is exactly (a, b)
```

These tests directly protect the intended semantics without requiring the full
`Vec`, `Option`, or `Pair` constructor family to exist first.

## 13. Return-Normal-Form Substrate

The implementation substrate for this contract is shape-level:

```text
EvalResultNormalForm = ValuePoint(e) | Product(P)
```

`question_view` follows the documented view-transition rules:

```text
Product(P) -> Product(P)
leaf e     -> e
non-leaf e -> exposed view
```

The current substrate may report this transitional shape category:

```text
ProductPattern + P -> Direct
ProductPattern + non-leaf e exposing P -> AfterExtraction
ProductPattern + leaf e -> Mismatch
```

`AfterExtraction` is not a final implicit-`?` rule. Final binding reads Pattern
directly, while explicit postfix `?` remains a separate one-layer operation.

A generated struct type records instance extraction metadata as a named field
product with value projections. The type-definition invocation value remains a
graph-uninstalled invocation value; declared symbols, associated namespaces,
field projections, and instance extraction metadata are binding materialization
artifacts. The current formal invocation may allocate registry-backed pattern
material, so graph-installation-free/binding-free is the precise guarantee.

## 14. core::struct Normalized-AST Decoding Contract

`core::struct` reads generic normalized AST and performs struct-specific
interpretation locally. The parser and normalizer are not modified for struct
syntax.

Contract-level invariants:

```text
1. The struct decoder (`struct_decoder.rs`) owns struct-specific interpretation
   of generic NormExpr nodes.
2. No parser or normalizer node is introduced for struct type-pattern
   expressions. The normalized AST remains generic.
3. `|` is the canonical sum-pattern result form accepted by the decoder.
   `+` is a pattern-combination reduction action and is not directly accepted
   as a canonical sum by the decoder.
4. The decoder produces TypePatternExprShape, which is attached to
   the current `GeneratedTypeDefinitionValue` substrate. In the final model this
   remains private structured carrier material inside the meta-construction
   carrier; AST is not the public return rank.
5. The decoder does not install NamespaceDelta. Only binding/materialization
   installs graph objects.
6. Leaf type expressions are not restricted to simple paths. The final bare
   Name in an application chain is the local field/payload name; the prefix is
   the type expression. This rule is struct-decoding-local only.
7. Semantically, a leaf `E name` keeps pattern-name identity (`name`) separate
   from leaf-value origin (`E`). `E` is resolved/evaluated through external
   symbol bindings, and different leaves need not share the same `E`.
```
