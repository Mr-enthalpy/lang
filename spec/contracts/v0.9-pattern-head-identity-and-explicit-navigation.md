# v0.9 Pattern Head Identity and Explicit Navigation

Contract for pattern head identity, bounded extraction lookup, and
the `::` explicit symbol navigation boundary.

**Status:** Implemented structure (parser/normalizer preserve the
distinction). Semantic resolution and D/Done are not implemented.

## 1. Symbol First-Rank Rule

The first rank of the symbol system is the symbol, not type, value,
pattern, or callable. A single path `P` resolves to different roles
depending on expectation context:

```text
namespace context:
  P → namespace node

type / annotation context:
  P → type-rank / pattern-rank object

value expression:
  P → value / callable object

extraction pattern:
  P → bounded extraction-scope child
```

The normalizer preserves structural distinction between bare names
and explicit nav paths but does not resolve roles.

## 2. Bare Name vs Explicit `::` Navigation

`::` is a universal explicit symbol navigation boundary. It applies
in expression, pattern, annotation, and namespace contexts.

| Form | Meaning |
|------|---------|
| `P1` | Automatic contextual lookup — may be completed to `P1::P2` in bounded extraction |
| `P1::` | Explicit terminated navigation — contextual completion is blocked |
| `P1::P2` | Explicit navigation path — no contextual completion |

Raw AST preserves the distinction via:

```text
AtomKind::NavPath {
    components: Vec<NavComponentAst>,
    explicit_terminated: bool,
}
```

`explicit_terminated: true` means the path was written as `P1::`
(trailing `::`), blocking contextual completion.

Normalized AST preserves the same distinction:

```text
NormExpr::Nav {
    components: Vec<NormNavComponent>,
    explicit_terminated: bool,
    origin: NormOrigin,
}

NormPattern::Nav {
    components: Vec<NormNavComponent>,
    explicit_terminated: bool,
    origin: NormOrigin,
}
```

## 3. `P::` as Explicit Terminated Navigation

The parser recognizes trailing `::` at the atom level and the
operator-nav level. Both produce `explicit_terminated: true`:

```lang
let x = P1::;         // explicit terminated nav
let val (P1::) P2 = e;  // group boundary terminates P1::
```

The normalizer preserves `explicit_terminated` in both expression-side
and pattern-side nav paths.

Whitespace after `::` does **not** terminate navigation. `::` consumes
the next valid navigation component across trivia (max-munch):

```text
P1::P2, P1:: P2, P1 :: P2    → all parse as P1::P2
```

To force termination before another same-level pattern atom, use
grouping `(...)`:

```text
let val (P1::) P2 = e;    // P1:: terminated, P2 separate binder
let val P1:: P2 = e;      // P1::P2 as single explicit nav path
```

The same applies in expression position: `P1:: (P2)` is an explicit
nav path with a group component `(P2)` (the parser accepts `(` as a valid
nav group component). To force termination before a group, use
`(P1::) (P2)`. Both `P1::P2` and `P1:: P2` are the same explicit nav path.

## 4. Bounded Extraction Lookup

In extraction patterns, bare names undergo bounded child lookup:

```text
let val P1 P2 = expr;
```

is interpreted as:

```text
H0 = top_pattern(expr)
H1 = lookup_extract_child(H0, P2)
H2 = lookup_extract_child(H1, P1)
```

The extraction structure itself forms the navigation path.
Bare names are NOT global lookups — they are bounded by the
current extraction context.

Explicit `::` names in extraction bypass bounded lookup:

```lang
let val (P1::) P2 = expr;
```

`P1::` is explicit terminated nav → do not complete to `P1::P2`
where P2 is the current extraction scope.

`P1::Q` is explicit nav `P1::Q` → do not complete to `(P1::Q)::P2`.

## 5. PatternHeadId Is Not Bare Spelling

A pattern head identity is not a bare string. It is:

```text
PatternHeadId = resolved_symbol_place_identity
              = PatternHeadId(<symbol>, <materialization context>)
```

The bare spelling `name` in source is just a display form. The
resolved identity depends on the materialization context:

```lang
((int a) name) |> struct
```

After materialization:

```text
global context:
  top pattern identity = name (resolved via global namespace)

namespace ns context:
  top pattern identity = name::ns (resolved via ns-qualified identity)

local materialization place:
  top pattern identity = name::__inner_place (local place identity)
```

Current implementation provides a build-local `PatternHeadId` plus
`PatternHeadRegistry`. The registry preserves the semantic origin material
used to allocate each head. `PatternHeadId` is:

- not a bare spelling;
- not a final `TypeValueId`;
- not a `PlaceId`;
- not equality by display name.

Implemented origins include global binding, namespace binding, local
materialization place, field, generated construction/type-definition, and
external forward. Local materialization identity uses `LocalPatternPlaceId`,
which is a build-local materialization identity, not a user-writable ordinary
symbol. The display name is supplied at allocation time and is recorded only
as diagnostic/dump material; local context identity does not carry a second
display-name source.

## 5.1 PatternHeadId Materialization Loop

The current v0.9 substrate closes this minimal loop:

```text
struct/type materialization context
  -> owner PatternHeadId
  -> field PatternHeadId
  -> extraction child scope
  -> bounded extraction lookup
  -> ConstructorHead
  -> ConstructedValue
  -> one-step ?
  -> reconstruction
  -> semantic equality
```

Owner heads are allocated from materialization context:

```text
Global(symbol_id)
Namespace(namespace_symbol_id, symbol_id)
Local(place_id)
Generated(construction_instance_id)
GeneratedTypeDefinition(type_definition_id)
```

Field heads are scoped by owner head:

```text
Field {
  owner_head,
  field_name,
  field_type_symbol_id,
  projection
}
```

The registry records:

```text
ExtractionChildScope(owner_head)[field_name] = field_head
```

The current implementation exposes this as a minimal materialization
boundary:

```text
PatternHeadRegistry::materialize_struct_pattern_heads(
  PatternMaterializationContext,
  display_name,
  fields
) -> PatternHeadMaterialization
```

This helper is the v0.9 substrate boundary for struct/type materialization.
It records owner and field heads and wires the field heads into the owner's
extraction child scope. It is still not full struct execution, full
extraction execution, or pattern-space algebra.

The current struct/type materialization path calls this helper from formal
`struct` invocation. `GeneratedTypeDefinitionValue` retains:

```text
pattern_heads.owner_head
pattern_heads.field_heads[field_name] = field_head
fields[i].pattern_head = field_head
```

Binding the generated type projects the same identities into the resulting
`TypeObject`, `TypeField`, extraction interface, and generated field-function
payloads. `CompilationWorld` owns the `TypeMaterializationState`; the registry
is not recreated and discarded for each source fixture.

Registration is conflict-aware:

```text
explicit path -> same head      idempotent
explicit path -> different head diagnostic
same owner + same field material idempotent
same owner + same field name + different material diagnostic
same field name under different owner allowed
```

The restricted lookup expectation boundary is explicit:

```text
AutoName + ExtractionChild -> bounded child lookup
AutoName + other expectation -> unsupported expectation diagnostic
ExplicitNav + any current v0.9 expectation -> explicit path table only
```

Therefore a bare pattern-side name in extraction context resolves against the
current owner head's child scope. Explicit `::` navigation does not use this
bounded completion and must resolve through the explicit path resolver.

`ConstructorHead` and `ConstructedValue` now carry `PatternHeadId`.
Semantic equality compares head identity and payload semantic equality; it
does not compare provenance or display name.

## 6. Context-Sensitive Struct Top Pattern Identity

When `struct` materializes a type definition, the top pattern
identity is determined by the materialization context, not
solely by the binder name in the struct pattern expression.

```lang
let Bounded = (self, t: type): meta -> _: type => {
    (t inner) |> struct;
};
```

The materialized type's top pattern name `Bounded` is a
context-sensitive identity that includes the declaration namespace.
In the global namespace, the top pattern is `Bounded`. In a
nested namespace `ns`, the top pattern identity is `Bounded::ns`
or equivalent namespace-qualified identity.

## 7. Value-Side Lookup Does Not Use Extraction Bounded Scope

On the value side, bare names use ordinary value/callable lookup:

```lang
inner_val inner    // value-side auto lookup of 'inner'
```

This does NOT use extraction bounded scope. To access a field
constructor explicitly, the full navigation path must be written:

```lang
inner_val inner::(uint Bounded)    // explicit field constructor nav
```

Or an alias must be established:

```lang
let inner === inner::(uint Bounded);
inner_val inner                    // now auto lookup through alias
```

The value-side resolver must distinguish:

```text
resolve_auto_name(name, context, expectation)

resolve_explicit_nav(path, explicit_terminated, context, expectation)
```

Both must be available to the resolver. The normalizer preserves
the distinction in AST/Norm structure.

## 8. Non-Goals

This contract does not implement or specify:

- D/Done reduction
- Done_Return
- Pack syntax or matching
- Full pattern-space algebra
- Layout / ABI lowering
- Borrow / access-tree checking
- Full role-aware resolver
- Semantic target resolution
- Bound-child extraction execution
