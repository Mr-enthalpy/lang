# v0.9 Pattern Head Identity and Explicit Navigation

Contract for pattern head identity substrate, bounded extraction lookup, and
the `::` explicit symbol navigation boundary.

**Status:** Mixed. Parser/normalizer preservation and the registry-backed
`PatternHeadId` substrate are implemented. Final symbol-first facet resolution,
`ResolvedPatternScope`, `struct` owner resolution, and functional `inject` are
future design and are not implemented.

The canonical future owner/construction model is
`spec/design/symbol-world/symbol-first-meta-construction-and-pattern-injection.md`.
Namespace origin and construction-unit ownership are canonical in
`spec/design/symbol-world/symbol-construction-units-and-namespace-origin.md`.
Where this contract describes current `PatternMaterializationContext` behavior,
that behavior is an implementation substrate, not the final semantic rule.

## 1. Symbol First-Rank Rule

The first rank of the symbol system is the symbol, not type, value, pattern, or
callable:

```text
path/name
  -> Symbol
  -> context-directed facet projection
```

A symbol may simultaneously have namespace, type, and heterogeneous value
facets. Namespace/type/value expectations project facets from the resolved
symbol; they do not cause the path to resolve into unrelated object categories.
An extraction pattern additionally resolves a bounded child within the current
`ResolvedPatternScope`.

Conceptually:

```text
namespace context:
  P -> Symbol -> namespace facet

type / annotation context:
  P -> Symbol -> type facet / PatternValue

value expression:
  P -> Symbol -> heterogeneous value facet

extraction pattern:
  current ResolvedPatternScope + P -> bounded pattern child
```

The normalizer preserves the structural distinction between bare names and
explicit nav paths but does not resolve symbols, facets, or pattern scopes.

## 2. Bare Name vs Explicit `::` Navigation

`::` is a universal explicit symbol navigation boundary. It applies
in expression, pattern, annotation, and namespace contexts.

| Form | Meaning |
|------|---------|
| `P1` | Automatic contextual lookup — may be completed to `P1::P2` in bounded extraction |
| `P1::` | Explicit terminated navigation — contextual completion is blocked |
| `P1::P2` | Explicit navigation path — no contextual completion |

Raw AST preserves the distinction via:

```text
AtomKind::NavPath {
    components: Vec<NavComponentAst>,
    explicit_terminated: bool,
}
```

`explicit_terminated: true` means the path was written as `P1::`
(trailing `::`), blocking contextual completion.

Normalized AST preserves the same distinction:

```text
NormExpr::Nav {
    components: Vec<NormNavComponent>,
    explicit_terminated: bool,
    origin: NormOrigin,
}

NormPattern::Nav {
    components: Vec<NormNavComponent>,
    explicit_terminated: bool,
    origin: NormOrigin,
}
```

## 3. `P::` as Explicit Terminated Navigation

The parser recognizes trailing `::` at the atom level and the
operator-nav level. Both produce `explicit_terminated: true`:

```lang
let x = P1::;         // explicit terminated nav
let val (P1::) P2 = e;  // group boundary terminates P1::
```

The normalizer preserves `explicit_terminated` in both expression-side
and pattern-side nav paths.

Whitespace after `::` does **not** terminate navigation. `::` consumes
the next valid navigation component across trivia (max-munch):

```text
P1::P2, P1:: P2, P1 :: P2    → all parse as P1::P2
```

To force termination before another same-level pattern atom, use
grouping `(...)`:

```text
let val (P1::) P2 = e;    // P1:: terminated, P2 separate binder
let val P1:: P2 = e;      // P1::P2 as single explicit nav path
```

The same applies in expression position: `P1:: (P2)` is an explicit
nav path with a group component `(P2)` (the parser accepts `(` as a valid
nav group component). To force termination before a group, use
`(P1::) (P2)`. Both `P1::P2` and `P1:: P2` are the same explicit nav path.

## 4. Bounded Extraction Lookup

In final extraction semantics, every Pattern layer has:

```text
OwnNavigation(layer) =
    Explicit(path)
  | ImplicitGlobal
  | Absent
```

Only a non-root layer may be `Absent`. A root Pattern with omitted navigation
is `ImplicitGlobal`, so the nearest non-`Absent` ancestor always exists.

```text
Anchor(x) =
  nearest ancestor a of x
  where OwnNavigation(a) != Absent

FullNav(x) =
  LocalSegments(x -> Anchor(x))
  :: Navigation(Anchor(x))
```

A bare name first undergoes bounded completion as a **symbol path**.
Completion walks the already established Pattern-parent chain from nearest to
farthest and stops at that nearest navigation anchor. The evaluator then
resolves the exact symbol path and reads its bound `PatternValue`:

```text
bare name + complete Pattern-parent chain
  -> append inherited parent components from nearest to farthest
  -> continue through OwnNavigation = Absent
  -> stop at nearest Explicit(path) or ImplicitGlobal
  -> completed symbol path
  -> resolve Symbol
  -> read PatternValue from Symbol
```

For a general extraction shape:

```text
let val P1 P2 = expr;
```

the extraction structure supplies the parent scopes used to complete `P2` and
then `P1`. This process does not distinguish internal from external Pattern
values; it observes only where the nearest parent has
`OwnNavigation != Absent`.

If no ancestor has `Explicit(path)`, the top Pattern's `ImplicitGlobal` state
is the anchor. An omitted navigation on that top Pattern means exact global
lookup (implicit `::`), not ordinary bare-symbol `near -> outer -> core`
search. Completion still produces symbol paths rather than directly exposing
pattern values.
The pattern expectation may read only a `PatternValue`/pattern interface from
the resolved symbol; it does not fall back to ordinary value/callable lookup.

Completion follows parent identities only. It never guesses an outer Pattern
by reversing or correlating resident names. A non-empty parent chain that ends
in `Absent` is incomplete/invalid rather than an implicit-global shortcut.

Explicit `::` navigation bypasses parent completion but follows the same
symbol-then-value flow:

```lang
let val (P1::) P2 = expr;
```

`P1::` is explicit terminated nav → do not complete to `P1::P2`
where `P2` is the current extraction scope. Resolve the explicit symbol path,
then read the `PatternValue` carried by that symbol.

`P1::Q` is explicit nav `P1::Q` → do not complete to `(P1::Q)::P2`.

Conceptually, `::external` means “start from this external symbol layer rather
than inheriting the current parent scope.” In the frozen inner-to-outer source
notation, explicit termination appears as `external::` where grouping is
needed. This is a symbol-path resolution distinction, not direct versus
indirect access to a value.

### 4.1 Future value lookup and extraction algebra

This contract requires the current syntax/registry substrate to preserve the
handoff boundary, but it does not duplicate the future pattern-value algebra.
The consistency requirements are:

```text
source path -> Symbol -> PatternValue
binding a value to another symbol does not reroot it
extraction membership compares PatternValue, not SymbolId or source spelling
```

The complete binding examples, fully named
`Map<CanonicalFullNavigation, CanonicalPatternValue>` semantics, idempotent
same-value insertion, and symbol-to-value-to-map lookup equation are canonical
in
`spec/design/symbol-world/symbol-first-meta-construction-and-pattern-injection.md`.
The broader extraction algebra belongs to
`spec/design/patterns-overload/static-pattern-spaces-and-extraction-chains.md`.
No current `PatternHeadId` API is evidence that those future value-set semantics
are implemented.

## 5. PatternHeadId Is a Transitional Registry Identity

A resolved pattern identity is never a bare string. The final model resolves:

```text
explicit relative pattern components
  + ambient ResolvedPatternScope
  -> fully resolved pattern path / PatternScopeId
```

The current implementation does not yet have `ResolvedPatternScope` or
`PatternScopeId`. It provides a build-local `PatternHeadId` plus
`PatternHeadRegistry`, and allocates owner heads from a categorical
`PatternMaterializationContext`. That is the current registry/materialization
substrate only; it must not be promoted into the final rule that a binding
destination determines pattern ownership.

The registry preserves the origin material used to allocate each current head.
Current `PatternHeadId` is:

- not a bare spelling;
- not a final `TypeValueId`;
- not a `PlaceId`;
- not equality by display name.

Implemented substrate origins include global binding, namespace binding, local
materialization place, field, generated construction/type-definition, and
external forward. Local materialization identity uses `LocalPatternPlaceId`,
which is a build-local materialization identity, not a user-writable ordinary
symbol. The display name is supplied at allocation time and is recorded only
as diagnostic/dump material; local context identity does not carry a second
display-name source.

In the final model, diagnostic projections such as `name::ns` remain structured
renderings of a resolved owner scope. They are not computed by concatenating a
binding path, and they are not evidence that the binding target rerooted the
right-hand pattern.

## 5.1 PatternHeadId Materialization Loop

The current v0.9 substrate closes this minimal loop:

```text
struct/type materialization context
  -> owner PatternHeadId
  -> field PatternHeadId
  -> extraction child scope
  -> bounded extraction lookup
  -> ConstructorHead
  -> ConstructedValue
  -> one-step ?
  -> reconstruction
  -> semantic equality
```

Owner heads are allocated from materialization context:

```text
Global(symbol_id)
Namespace(namespace_symbol_id, symbol_id)
Local(place_id)
Generated(construction_instance_id)
GeneratedTypeDefinition(type_definition_id)
```

Field heads are scoped by owner head:

```text
Field {
  owner_head,
  field_name,
  field_type_value,
  projection
}
```

`field_type_value` is the evaluated `TypeValueId`. A source carrier Symbol may
be retained separately as provenance or namespace-navigation material, but it
does not participate in field-head identity. Ordinary type-value rebinding
therefore cannot create a second field Pattern merely by changing the spelling
used to obtain the same type value.

The registry records:

```text
ExtractionChildScope(owner_head)[field_name] = field_head
```

The current implementation exposes this as a minimal materialization
boundary:

```text
PatternHeadRegistry::materialize_struct_pattern_heads(
  PatternMaterializationContext,
  display_name,
  fields
) -> PatternHeadMaterialization
```

This helper is the v0.9 substrate boundary for struct/type materialization.
It records owner and field heads and wires the field heads into the owner's
extraction child scope. It is still not full struct execution, full
extraction execution, or pattern-space algebra.

The current struct/type materialization path calls this helper from formal
`struct` invocation. `GeneratedTypeDefinitionValue` retains:

```text
pattern_heads.owner_head
pattern_heads.field_heads[field_name] = field_head
fields[i].pattern_head = field_head
```

During formal invocation, the fallback owner head is derived from the generated
type-definition identity rather than an eventual declaration binder. Cache
transport may strip concrete registry IDs; binding restores stripped material
under the same anonymous generated fallback and preserves material that is
already attached. The explicit helper API separately supports categorical
global, namespace, and local contexts for low-level registry tests, although
full local Self-frame lowering is not wired.

Status: this is the current `struct` invocation/attachment substrate. It
preserves registry continuity and supports explicit low-level context
attachment, but ordinary binding does not derive a context from its destination
and this remains short of the final owner-resolution model. Final `struct`
ownership is resolved before binding from input pattern navigation plus ambient
pattern scope; the binding destination does not reroot it.

After preserving or restoring provisional material, binding projects the
resulting identities into the `TypeObject`, `TypeField`, extraction interface,
and generated field-function payloads. `CompilationWorld` owns the
`TypeMaterializationState`; the registry is not recreated and discarded for
each source fixture.

Meta invocation caching stores replayable type-definition material, not
concrete registry-backed `PatternHeadId`s. On cache miss, struct invocation
materializes heads in the caller's `TypeMaterializationState` and caches a
sanitized `GeneratedTypeDefinitionValue` with pattern-head fields removed. On
cache hit, the cached value is rehydrated by rerunning the pattern-head
materialization step in the current `TypeMaterializationState` before it is
returned. This preserves both constraints:

```text
MetaInstanceCache remains a pure invocation-material cache.
PatternHeadId remains registry-backed semantic identity.
```

Standalone compatibility wrappers that create a temporary
`TypeMaterializationState` are suitable only for one-off expansion tests. Build
or semantic paths that need later bounded lookup must use the
`*_with_materialization_state` entry points or `CompilationWorld`'s owned
state. The current source build main path uses the stateful entry point, not
the standalone wrappers.

Registration is conflict-aware:

```text
explicit path -> same head      idempotent
explicit path -> different head diagnostic
same owner + same field material idempotent
same owner + same field name + different material diagnostic
same field name under different owner allowed
```

The restricted lookup expectation boundary is explicit:

```text
AutoName + ExtractionChild -> bounded child lookup
AutoName + other expectation -> unsupported expectation diagnostic
ExplicitNav + any current v0.9 expectation -> explicit path table only
```

Therefore a bare pattern-side name in extraction context resolves against the
current owner head's child scope. Explicit `::` navigation does not use this
bounded completion and must resolve through the explicit path resolver.
Pattern-side names do not fall back to ordinary value/function lookup.

`ConstructorHead` and `ConstructedValue` now carry `PatternHeadId`.
Semantic equality compares head identity and payload semantic equality; it
does not compare provenance or display name.

## 6. Final Struct Owner Is Scope-Resolved, Not Binding-Injected

The final owner rule is:

```text
struct owner
  = resolve(input pattern's explicit relative navigation,
            ambient ResolvedPatternScope)

binding/injection target
  = resolve left-side path with the installation-place judgment
```

These judgments are independent. `struct` does not inspect the left-side
binding target and binding does not reroot the right-hand pattern.

For every construction value `V`:

```text
install_place(V)
pattern_owner(V)
```

may differ. Therefore:

```lang
let t1::t = (...) |> struct;
```

installs the right-hand construction at the place denoted by `t1::t`, but the
right-hand pattern owner remains the scope resolved by ordinary `struct`
navigation. To choose `t1::t`'s internal pattern scope as owner, source must use
the explicit future `inject` operation described by the canonical symbol-first
document.

An ordinary meta-function instance is itself a navigable pattern scope. Named
and single-field constructions use the same rule:

```text
explicit relative pattern components
  + ambient navigable pattern scope
  -> fully resolved pattern path
```

There is no separate semantic path based on whether a source expression appears
to contain an independent outer pattern name.

### 6.1 Meta return type root is the meta-instance scope

For an ordinary canonical meta invocation:

```text
M = MetaInstanceScope(callee_symbol, canonical_arguments)
```

the return symbol's type facet, when present, must satisfy:

```text
type_facet(r) = tau
  => root_pattern_scope(tau) = M
```

This identity is decided before outer binding and cannot be rerooted by the
destination place. Direct meta type returns `r = t` and `r = uint8` are invalid
when `t`/`uint8` carry externally rooted `PatternValue`s. A legal meta body may
construct `(t inner::(t f))::(t f)` through `struct`, or include an external
`PatternValue` as a member beneath `(t f)`.

`compile` is not subject to this rule. It returns a `PatternValue`, creates no
`MetaInstanceScope`, and uses the ordinary function-object internal Self frame
for local `struct` ownership.

The corresponding namespace-origin and construction-unit ownership rules are
in
`spec/design/symbol-world/symbol-construction-units-and-namespace-origin.md`.

### 6.2 Current Implementation Substrate

Formal `struct` invocation currently uses
`GeneratedTypeDefinition(type_definition_id)` as a cache-safe fallback:

```text
formal struct invocation
  -> GeneratedTypeDefinitionValue
  -> PatternMaterializationContext::GeneratedTypeDefinition { type_definition_id }
  -> registry-backed owner PatternHeadId
```

Formal invocation is graph-installation-free and binding-free: it does not
install `NamespaceDelta`. It may allocate or attach registry-backed pattern
material, so it must not be described unconditionally as pure.

Current PR #94 substrate:

```text
explicit context attachment helper
Generated / GeneratedTypeDefinition / Global / Namespace / Local context categories
ordinary binding preserves attached provisional owner material
GeneratedTypeDefinition fallback for formal invocation, cache replay, and stripped binding input
registry-backed owner/field PatternHeadId and bounded child lookup
```

The categorical contexts are transitional low-level registry inputs, not final
language owner scopes. Ordinary binding does not derive one from its destination
path and therefore does not select or reroot provisional owner identity.
The explicit-context helper is doc-hidden transitional test support, not a
stable external API for manufacturing pattern owners. Its public Rust
visibility exists only so integration tests can exercise registry categories.

## 7. Value-Side Lookup Does Not Use Extraction Bounded Scope

On the value side, a bare name resolves a symbol and projects its heterogeneous
value facet. It does not use extraction bounded scope:

```lang
inner_val inner    // value-side auto lookup of 'inner'
```

This does NOT use extraction bounded scope. To access a field
constructor explicitly, the full navigation path must be written:

```lang
inner_val inner::(uint Bounded)    // explicit field constructor nav
```

Or the constructor value must be bound to an ordinary name first:

```lang
let inner = inner::(uint Bounded);
inner_val inner                    // auto lookup of the new symbol
```

This is an ordinary binding, not a lookup forwarding. It creates a fresh symbol
in a fresh place whose value is the constructor value:

```text
SymbolId(inner)  ≠ SymbolId(inner::(uint Bounded))
PlaceId(inner)   ≠ PlaceId(inner::(uint Bounded))
Value(inner)     =  Value(inner::(uint Bounded))
```

Subsequent auto lookup of `inner` resolves the new symbol directly; it does not
re-enter the navigation path.

In a call position, candidate preparation then obtains each value's type and
looks for its type-associated `()` entry; non-callable values are discarded.
The value-side resolver must still distinguish:

```text
resolve_auto_name(name, context, expectation)

resolve_explicit_nav(path, explicit_terminated, context, expectation)
```

Both must be available to the resolver. The normalizer preserves
the distinction in AST/Norm structure.
