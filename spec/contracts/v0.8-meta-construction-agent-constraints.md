This document is not a new language design overview and does not replace any
existing specification text. It is a construction-constraint document for future
engineering agents working around v0.8, especially on ordinary generic
type-style meta-function capability such as `(T Vec)`, `(T Option)`, and
`(A, B Pair)` symbol constructions.

The older formal return split (`r = ...` generated versus `r === ...`
forwarded) is superseded. Final formal meta return uses `r = ...` to populate a
`SymbolConstruction`. The semantic alias/forwarding direction is retired: there
is no ordinary symbol-alias or place-forwarding declaration form.

Its core purpose is to prevent agents from implementing a local feature through
an ad hoc bypass that happens to work in isolation, while damaging the shared
semantic foundation across build/package, symbol-world, patterns-overload,
product normalization, policy-capability, meta-invocation, and mechanical
lowering.

The project takes a long-term implementation approach. Implementation may be
staged, use placeholders, or use stubs, but object boundaries and semantic
direction must not be rewritten for short-term convenience.

## 1. General Principle: Advance the Closed Loop, Not Isolated Points

Any v0.8-related implementation task must not make progress from a single module
alone. For example:

- Do not create a special execution path only for `struct`.
- Do not recognize `(T Vec)` through a name check or AST-shape check.
- Do not temporarily parse arguments only for one generic type constructor.
- Do not let the type checker, meta interpreter, policy checker, and resolver
  maintain parallel symbol tables.
- Do not let product argument reading bypass pattern / argument-shape objects.
- Do not make policy apply only at lookup time or only at execution time.
- Do not let build/package identity disappear from candidate identity, meta
  instance keys, provenance, or cache keys.

Every implementation point must be checked against this loop:

```text
build/package identity
  -> namespace graph / SymbolCell (current substrate: SymbolObject)
  -> SymbolId / PlaceId / PatternValue / TypeValueId / AliasChain
  -> ProductObject / ArgProductShape / RawArgShape / ParameterShape
     (explicit user product only; self is invocation-frame slot 0)
  -> heterogeneous value-object enumeration
  -> per-object P1 candidate filtering
  -> structural applicability and P2 qualification
  -> formal meta invocation
  -> layered PatternValue or SymbolConstructionValue result
  -> binding/install adapter (current substrate: MetaExpansionResult)
  -> NamespaceDelta atomic install
  -> generated instance identity / provenance / diagnostics
```

If one stage is not fully implemented yet, use a placeholder. The placeholder
must live in the correct object slot; it must not create a new bypass semantic.

## 2. No-Bypass Rule

Every component that needs symbols must go through the shared namespace graph
world model.

This includes, but is not limited to:

```text
resolver
early meta-function lookup
struct
assert
verify
generic type meta-functions
type checker
policy checker
seal stage
IDE index
cache layer
diagnostics
later HIR lowering
```

Forbidden:

```text
parser special-cases self / Self / return / struct / verify / () / Vec / Pair
normalizer special-cases self / Self / return / struct / verify / () / Vec / Pair
meta executor searches raw string names outside resolver
type checker maintains private global symbol map
policy checker re-resolves by string path
generic instantiation key uses source text only
core symbols are globally visible through ambient state rather than explicit graph mount
```

The only permitted bootstrap magic is a compiler-seeded core package artifact,
a default core mount, and built-in payload placeholders. Even then, those symbols
must be installed into the namespace graph and returned by the resolver as
ordinary `SymbolObject`s.

## 3. Target Stage: Ordinary Generic Type-Style Meta-Functions

For the canonical symbol-first/facet model, `compile` / `meta` result split,
rank-directed canonical identity, `struct` ownership, functional `inject`, and
binding/install boundary, see
`spec/design/symbol-world/symbol-first-meta-construction-and-pattern-injection.md`.
For extraction-view and product-return details, see
`spec/contracts/v0.8-symbolic-construction-values-and-extraction-interfaces.md`.

The current target is not full metaprogramming, full runtime overload,
value-to-value compile-time execution, a full type checker, or a full policy
lattice.

The target is the earliest restricted path toward symbol construction:

```text
compile inputs -> PatternValue
meta inputs -> SymbolConstructionValue : symbol
single entry / single exit
no intermediate control flow
meta body is Normalized AST
construction is graph / delta / policy governed
```

Typical targets:

```text
(T Vec)
(T Option)
(A, B Pair)
```

These targets must be implemented as ordinary graph-resolved meta callables, not
compiler special cases.

A valid generic type-style meta-function invocation should follow this flow:

```text
resolve callee symbol through namespace graph
collect callable candidates under lookup policy
form ProductObject / ArgProductShape
form per-element RawArgShape
match ParameterShape and rank-directed SymbolId / TypeValueId / PatternValue compatibility
check current body-entry metadata admits Meta
invoke primitive or type-to-type construction interpreter
produce PatternValue / SymbolConstructionValue / Residual / Diagnostic
compute canonical meta instance key
bind to an independently resolved writable PlaceId
install NamespaceDelta atomically
retain canonical Pv:Pp on returned Val1 / Pattern entries and independent
policy pairs on returned Val2 objects; any outer binding P1 then selects a view
```

`ProductObject`, `ArgProductShape`, and `RawArgShape` describe only the
explicit user-supplied argument product. Caller self is injected by the
invocation frame into callable-frame slot 0 after callable resolution. It must
not be counted in product arity, product flattening, canonical argument
products, or meta instance keys. For every ordinary or in-place closure, the
first written formal is the explicit Pattern for slot 0 regardless of binder
spelling. Only later written formals align with explicit Product positions.

For `struct`, `pattern_owner(V)` is resolved from input navigation plus ambient
`ResolvedPatternScope` before binding. `install_place(V)` is resolved by the
outer `let` binding/injection judgment. The latter must never reroot the former.

## 4. Product Semantic Normalization Must Become a Precondition Contract

Existing public docs define surface product / pipe / call binding. v0.8 needs an
additional semantic-layer `ProductObject` normalization. This rule must not be
conflated with surface normalization.

Core rules:

```text
flatten crosses Product nodes.
flatten does not cross Expression nodes.
order is preserved.
Unit is preserved.
provenance is preserved.
```

Definition:

```text
NF_P(P) = ordered sequence of product atoms

NF_P((x1, x2, ..., xn))
  = concat(NF_item(x1), NF_item(x2), ..., NF_item(xn))

NF_item(Product p)
  = NF_P(p)

NF_item(Expression e)
  = [e]

NF_item(Unit)
  = [Unit]
```

Examples:

```text
((P, e), e)   -> (P, e, e)
((e, e), e)   -> (e, e, e)
((e, P), e)   -> (e, P, e)
(e, (P, e))   -> (e, P, e)
```

If `P` is still a product, continue flattening until the product spine contains
no exposed Product child nodes.

"Exposed P" means a Product child node directly exposed in product context. A
product already absorbed by an expression/call node is not exposed. Flattening
does not cross expressions.

Therefore:

```text
((a, b), c)
=> (a, b, c)

(a, (b, c))
=> (a, b, c)

((a |> f), (b, c))
=> (a |> f, b, c)

((a, b) |> f, c)
=> ((a, b) |> f, c)
```

Incorrect rule:

```text
((a, b) |> f, c)
=> (a, b, f, c)        // forbidden
```

This is forbidden because `(a, b) |> f` is an Expression barrier.

However, a call may locally normalize its own source product:

```text
Call(source = ((a, b), c), target = f)
=> Call(source = (a, b, c), target = f)
```

This is not crossing an Expression from the outside. It normalizes the source
product inside that call.

`ProductObject` must not silently drop `Unit`:

```text
((a,), b)
=> (a, Unit, b)

((), a)
=> (Unit, a)
```

Only a future explicit parameter expectation / extraction rule may eliminate
`Unit`. Product semantic normalization itself does not.

## 5. Minimum ProductObject / ArgProductShape Requirements

Before entering meta invocation / generic type constructors, a normalized
product must be converted into semantic objects. The recommended minimum object
layers are:

```text
NormProduct
  -> ProductObject
  -> FlattenedProductObject
  -> ArgProductShape
  -> per-element RawArgShape
```

`ProductObject` must preserve at least:

```text
original normalized product
flattened atom sequence
arity
unit positions
nested product provenance
source spans / origins
material role
```

`FlattenedProductObject` invariants:

```text
ordered sequence of atoms
no direct Product atom remains
Expression nodes are opaque
Unit is preserved
left-to-right order preserved
provenance preserved
```

`ArgProductShape` is input to candidate preparation. It is not a type-checker
result and not a runtime ABI argument list.

Each atom forms one `RawArgShape`, marking at least:

```text
is value?
explicit pass mode?
known first-order TypeValueId?
rank/type object?
namespace object?
meta object?
pattern object?
residual/runtime expression?
origin/provenance
```

Parameter matching for type-level generic callables must not trigger automatic
argument passing. Type objects, rank objects, namespace objects, meta objects,
and pattern objects are not value arguments and must not receive inserted
`copy/ref/share/move/in` actions.

Self injection is also not automatic argument passing through product shape. It
belongs to `InvocationFrame` / callable-frame construction, not to
`ProductObject`, `ArgProductShape`, or `RawArgShape`.

## 6. Symbol / Place / PatternValue Must Not Be Merged

Any generic type meta implementation must preserve:

```text
SymbolId
PlaceId
TypeValueId
PatternValue identity
ResolvedPatternScope / PatternScopeId
```

Meanings:

```text
SymbolId    = symbol object identity in the namespace graph
PlaceId     = location identity that can be bound, updated, injected into, or opened for a NamespaceDelta
TypeValueId = canonical type value identity
PatternValue identity = canonical compile-time value/pattern identity
PatternScopeId = navigable pattern-owner identity
```

Forbidden:

```text
TypeValueId equality implies PlaceId equality
SymbolId equality implies TypeValueId equality
PatternValue equality implies SymbolId or PlaceId equality
binding PlaceId determines struct PatternScopeId
a second name can be made to share another symbol's place
type-value equality grants write permission
```

Semantics of `let T: type = uint8`:

```text
symbol(T) = fresh symbol
place(T) = fresh writable place at current lexical level
type_value(T) = type_value(uint8)
```

There is no second declaration form with different place semantics. Every
binding allocates a fresh place; the frozen `let T === uint8` surface form has
no target semantics (see
`spec/design/symbol-world/entity-alias-design.md`). Where one place must be
observed through another name, the value held is a borrow view (`ref` / `share`
/ `@`).

`let f::T = ...` uses a place judgment, not a value judgment. Namespace
extension is a place operation, not a type-value operation.

## 7. Borrow Views and Generic Arguments

Generic type-style meta-functions must distinguish query modes over an
argument. There is no alias chain to follow, but a borrow view is not the same
object as its target, so at least three query modes must be distinguished:

```text
type-value evaluation:
  read the value; a `type ref` / `type share` view reads through to its target

callable lookup:
  policy-aware symbol resolution; a view is its own value and its member set
  is not silently that of the target

extension-place target:
  resolve the place, then check writability and extension eligibility
  Eligible(view of p) <= Eligible(p)
```

Do not encode view transparency as a global boolean. A view behaves differently
in type-value position, callable target position, and extension-place position.

A borrow view must carry at least:

```text
target place
target lifetime / observation region
whether the view is `ref` or `share`
writability of the view (share carries none)
extension eligibility, bounded by the target's own
```

No provenance chain, no forwarding chain, and no cycle detection are required,
because a view is one edge to a place, not a rewritable chain of symbols.
Idempotence is a rule of the operation, not a chain to walk:
`Borrow(Borrow(q)) = Borrow(q)`.

## 8. P1 and P2 Elaborate the Canonical Policy Pair

Canonical internal policy is:

```text
Π = Pv:Pp
```

where `Pv` describes the value component and `Pp` describes its carried
Pattern/anonymous-type component. Stage, value mutability, value presence,
ordinary namespace visibility, and export-root are typed orthogonal dimensions. A scalar policy
is surface shorthand or a derived summary only.

`P1` is the optional projection prefix on any binding:

```text
[P1] let x = e
```

Omitted `P1` retains the complete inferred result. A single `Q` is a
value-dominant projection and retains the Pattern associated with every
selected value. An explicit `Qv:Qp` filters both components. Therefore the
single form `Q` is not normalized to `Q:Q`.

General runtime binding remains legal:

```text
Gamma |- e : (tau, Pv:Pp)
selected = ProjectP1(P1, e)
selected is non-empty
selected <= destination policy
--------------------------------
Gamma |- [P1] let x = e
```

A source-side premise such as `Psrc != runtime` belongs only to the particular
compile-flow projection rule that states it. Agents must not move it onto
general `let` lowering or reject `binding_policy == runtime`.

`P2` describes the call/expression result pair. In P2 context only, a scalar
stage policy normalizes as:

```text
N2(P) = P:(P - runtime)        when P - runtime is non-empty
N2(runtime) = runtime:compile
```

An explicit P2 pair forbids runtime in `Pp` and requires any static stage in
`Pv` to agree with `Pp`. Function-object stage views are then derived from the
result pair:

```text
Stage(P1p) = Stage(P2p)
Stage(P1v) = Stage(P2v) union Stage(P2p)
```

This derivation applies only to stages. Result const/mut, namespace visibility,
and value presence do not propagate to the function object. An explicit P1 at
the declaration then projects the derived object view like any other binding.

The result remains layered `Val1 x Pattern x Val2` material. There is no scalar
lookup policy for the whole result.
Returned value/Pattern pairs retain their `Pv:Pp`; each returned `Val2` object
retains its own pair.

Forbidden inference:

```text
symbol visible in compile lookup
=> callable entry executable as compile or meta
```

Correct inference:

```text
ResolveSymbol(path) succeeds
=> the symbol identity exists independently of phase exposure

ExposePolicySlice(symbol, OpenStatic) exposes a meta/compile facet
=> the current static pass may inspect / classify / residualize that facet

current body-entry metadata admits Meta
=> meta pass may enter / evaluate callable body
```

For ordinary generic type-style meta-functions, the minimum requirements are:

```text
the normalized P2 result pair is meta:meta
the derived function-object stage view contains meta
callee payload is callable/meta-callable
implicit self and explicit arguments satisfy their declared pair patterns
public meta return rank is symbol; TypeFacet is validated inside construction
returned layers retain their component policy pairs
returned Val2 objects retain their own policy pairs
```

The current implementation does not expose this final source model. It stores
symbol policy, `body_entry_policy`, and `return_object_policy` metadata. Agents
must preserve those fields where current code depends on them, but must label
the return-object field transitional and must not treat it as a whole-result
policy slot.

The current branch includes typed structural compile-flow projection and
derived-companion exposure substrate. End-to-end evaluator integration,
must-select enforcement in every call path, automatic require, and complete
graph-wide pair storage remain incomplete.

## 9. Generic Meta Instance Identity

Ordinary generic type-style meta-functions must have a canonical meta instance
key. Source text or normalized dumps are forbidden as the only identity.

Minimum key:

```text
callee function SymbolId
canonical argument product
canonical argument identities by parameter rank:
  symbol -> SymbolId / observed PlaceId
  type   -> canonical observation of the evaluated type object
            (Addr(Norm_type); the bare TypeValueId is only the
            first-order root projection, not the argument identity)
  value  -> PatternValue identity
package identity
mount identity if relevant
build/config fingerprint
policy/export/provenance-relevant metadata
```

Examples:

```text
key((T Vec)) =
  SymbolId(Vec)
  + ArgProductShape([TypeSymbol(T)])
  + build/config fingerprint

key((A, B Pair)) =
  SymbolId(Pair)
  + ArgProductShape([TypeSymbol(A), TypeSymbol(B)])
  + build/config fingerprint
```

Product canonicalization must happen before key computation. Exposed Products
must be flattened in order; Expression barriers must not be crossed; whether
`Unit` participates in the key must be defined by the `ProductObject` contract,
not guessed by implementers.

The complete invocation is one navigation atom. If the callee is `Vec::std`,
the instance is `(T Vec::std)` and a child is `child::(T Vec::std)`. The forms
`(T Vec)::std` and unparenthesized `T Vec::std` do not denote that instance.

An ordinary canonical meta invocation also establishes a virtual construction
scope:

```text
M = MetaInstanceScope(callee_symbol, canonical_arguments)
```

If the return symbol has a type facet, its outer pattern root must be `M`.
Direct meta type returns `r = t` and `r = uint8` are therefore invalid when the
right side is an externally rooted `PatternValue`. This requirement does not
apply to `compile`, which creates no `MetaInstanceScope` and may return an
existing type value directly.

## 10. Meta Expansion and NamespaceDelta Atomicity

Any meta symbol construction must be installed through a transaction-shaped
result. A `compile` invocation computes a `PatternValue` and does not itself
install a symbol or namespace delta.

The invocation and binding layers carry distinct materials:

```text
PatternValue:
  compile-time value / type value / structured pattern value

SymbolConstructionValue from ordinary meta:
  fresh return symbol identity
  symbol/facet/pattern construction material
  non-root assigned value/member may equal an existing PatternValue
  TypeFacet root, when present, equals its canonical MetaInstanceScope
  resolved pattern owner
  diagnostics provenance
  construction identity material

Binding/install adapter (current substrate: MetaExpansionResult):
  replacement_object
  namespace_delta
  diagnostics
  provenance
  cache_key_fragment
```

Rules:

```text
success:
  install replacement and namespace delta as one unit

failure:
  install no generated symbols
  retain diagnostics
  leave no partial generated namespace subtree
```

This rule applies to:

```text
struct
inject result binding
(T Vec)
(T Option)
(A, B Pair)
future meta symbol constructions
```

Forbidden:

```text
formal struct/inject directly installing graph state
binding target rerooting an already resolved pattern owner
installing a half-generated type object and adding field functions later
leaving a partial type-associated namespace after failure
letting diagnostics depend on half-installed graph state
```

## 11. `struct` Must Migrate Toward Shared Meta Invocation

The current `struct` path may exist as a vertical slice, but new ordinary
generic type-style meta-functions must not expand that bespoke path.

Target direction:

```text
current struct / verify path
  -> shared meta invocation client

resolve callee
collect candidates
match ProductObject / ArgShape / TypeSymbol
check current body-entry metadata / future stage and parameter-pair rules
invoke primitive or interpreter
produce PatternValue or SymbolConstructionValue
materialize binding/install adapter
install delta atomically
```

The `struct` payload may be primitive. Its lookup, argument parsing, policy, and
delta installation must not split into a separate mechanism from ordinary
generic type meta-functions.

The current PR #94 context-attachment helper and
`GeneratedTypeDefinitionValue` fallback are transitional registry substrate.
They do not implement `ResolvedPatternScope`, binding-independent owner
resolution, `SymbolConstructionValue`, or functional `inject`.

## 12. Build Layer Must Enter Candidate Identity

The package/build layer is not external engineering scaffolding. It produces the
namespace graph and determines candidate search boundaries.

Every candidate object, meta instance, generated symbol, diagnostic, and cache
fragment must preserve sufficient build identity:

```text
package identity
namespace root
source root contribution
dependency mount
export surface
manifest/config fingerprint
provenance
```

Forbidden:

```text
candidate identity = raw path string only
generated type identity = callee name + source text only
external/internal visibility ignored
dependency mount identity ignored
```

## 13. Minimum Construction Order

Recommended stage order:

```text
1. Stabilize the ProductObject / ArgProductShape contract
2. Stabilize SymbolCell facets and minimum PatternValue / TypeValueId /
   PlaceId / AliasChain objects
3. Stabilize callable signature objects for compile/meta construction
4. Stabilize current policy metadata while shaping Pv:Pp, P1 projection,
   P2 normalization, and function-object stage derivation
5. Stabilize canonical meta instance keys
6. Stabilize NamespaceDelta atomic install for meta instances
7. Add SymbolConstructionValue and ResolvedPatternScope boundaries
8. Gradually migrate struct / verify to the shared invocation frame
9. Add functional child-only inject with outer binding installation
10. Implement restricted construction such as (T Vec) / (T Option) / (A, B Pair)
```

Do not skip steps 1, 2, 4, or 5 and directly implement `(T Vec)`.

Early extraction-pattern work has a narrower next-stage target:

```text
NormPattern / let-left material
  -> ExtractionPatternTree
  -> HoleCapture list
  -> ResolvedPatternHead list
  -> well-formedness diagnostics
```

It must not implement implicit pattern-directed `?`, execute RHS extraction,
recursively peel values, implement Done / residual / sum exhaustiveness, or
integrate access-tree checking.

## 14. Closed-Loop Checklist for Every PR / Patch

Any patch involving build, symbol, pattern, product, policy, meta, or generic
type construction must answer:

```text
Build:
  Does this object carry the needed package/mount/provenance/fingerprint slots?

Namespace graph:
  Does it work through SymbolObject / NamespaceDelta?
  Does it bypass the resolver?

Symbol identity:
  Does it resolve Symbol first, then project facets?
  Does it distinguish SymbolId / PlaceId / PatternValue / TypeValueId / PatternScopeId?
  Does it incorrectly derive writable place from type equality?
  Does a binding target incorrectly reroot struct pattern ownership?

Product:
  Does it go through ProductObject / ArgProductShape?
  Does it define exposed Product flattening?
  Does it preserve Unit / order / provenance?
  Does it avoid crossing Expression?
  Does it keep self out of explicit product shape?

Pattern / candidate:
  Does it form RawArgShape / ParameterShape?
  Does it avoid hardcoding full overload early?

Policy:
  Does it store or elaborate canonical Pv:Pp rather than one scalar policy?
  Does omitted P1 infer, single P1 project by value, and pair P1 filter both components?
  Does P2 normalize runtime to runtime:compile while preserving explicit runtime:seal?
  Does any non-runtime premise remain attached to its projection source P_src/P₁?
  Does it derive function-object stage P1 from P2 without copying mutability or namespace policy?
  Does it label current return-object metadata as transitional rather than a whole-result policy?
  Does it avoid the meta-visible => meta-executable error?

Meta invocation:
  Does it enter the shared invocation frame?
  Does compile return PatternValue and meta return SymbolConstructionValue?
  Does compile avoid creating a MetaInstanceScope?
  Does an ordinary-meta return TypeFacet root equal its MetaInstanceScope?
  Does formal invocation remain graph-installation-free?
  Does it support future strict/partial boundaries?

Pattern construction:
  Does struct resolve owner from input navigation + ambient scope?
  Is inject functional, child-only, and owner-preserving?
  Does only a fully named body of a Pattern normalize to
    Map<CanonicalFullNavigation, CanonicalPatternValue>?
  Does every naked Product remain positional even when all children are named?
  Are source category and provenance excluded from PatternValue identity?
  Does any bare child make its Pattern body positional?
  Does future `?` erase only the top Pattern name while retaining an anonymous
    Pattern-layer boundary and its existing ordering?

Invocation frame:
  Does this patch keep self out of ProductObject / ArgProductShape?
  Does the callable formal frame still have self slot 0?
  Does the first written formal denote slot 0 without requiring the spelling `self`?
  Do only later formals consume explicit Product positions?
  Does a zero-user-argument callable still carry self-position?

Delta atomicity:
  Does failure install no partial generated subtree?
  Does one construction unit own every created child subtree?
  Does the patch reject cross-file reopening rather than only duplicate names?

Alias:
  Is alias transparency distinguished by usage?
  Does it avoid manufacturing writable permission through aliasing?

Mechanical lowering:
  Does it avoid putting pass mode into TypeValueId?
  Does it avoid inserting pass actions for non-value arguments?
```

If any answer is unclear, do not continue expanding implementation features.
First add the contract or placeholder slot.

## 15. Minimum Requirements for Agents Reading This Document

Before executing v0.8-adjacent tasks, an agent must absorb at least these rules:

1. Treat this file as a construction plan, not as a replacement specification.
2. In the work plan, explicitly list the closed-loop nodes involved in the task:
   build, symbol, product/pattern, policy, meta invocation, and delta.
3. Before proposing an implementation, state whether there is any risk of
   bypassing the namespace graph, `SymbolObject`, `ProductObject`, or the
   `P1` / `P2` boundary.
4. If the current code lacks an object, do not replace it with an ad hoc
   substitute. Prefer creating a placeholder object, metadata slot, or
   contract-shaped API.
5. If a shortcut is temporarily unavoidable, mark it as an implementation
   limitation in code comments, test names, or docs. Do not present it as
   language semantics.
6. Every new test must cover at least one invariant, not merely demonstrate a
   feature.
7. When handling generic type-style meta-functions, assume by default that
   `struct`, `(T Vec)`, `(T Option)`, and `(A, B Pair)` ultimately belong to the
   same shared meta invocation frame.
8. When handling product arguments, use the rule: exposed Products flatten in
   order, Expression barriers are not crossed, `Unit` is not dropped, and
   provenance is not dropped.
9. When handling policy, keep `P1` binding projection distinct from `P2`
   result-pair normalization, derive function-object stage views from `P2`,
   and preserve current result-policy metadata only as transitional transport,
   not `P3`.
10. When handling aliases, distinguish type-value evaluation, callable lookup,
    and injection-place target usage.
11. When handling meta returns, use `r = ...` for construction material; do not
    reintroduce formal `r === ...` forwarding semantics.
12. When handling `struct`, keep `pattern_owner(V)` independent from
    `install_place(V)`; functional `inject` requires the current construction
    unit's owned, open/uninstalled construction handle and must not reopen an
    arbitrary installed symbol.
13. When handling meta type results, require the return type root to equal the
    ordinary-meta canonical `MetaInstanceScope`; do not accept identity-style
    `r = t`.
14. When handling namespace contributions, preserve one `NamespaceOrigin` and
    one construction owner per created subtree; do not reopen it across files.

Minimum acceptance standard:

```text
An agent's plan must mention:
  ProductObject / ArgProductShape
  SymbolCell (or current SymbolObject substrate)
  PatternValue / TypeValueId / PlaceId / AliasChain
  SymbolConstructionValue / ResolvedPatternScope
  canonical Pv:Pp, P1 projection, P2 normalization, plus transitional metadata
  canonical meta instance key
  NamespaceDelta atomicity
  no-bypass rule
```

If these terms do not appear, the plan has not absorbed this construction
document.
